|---|---|---|
| 1 | タイムゾーン | すべて日本標準時（JST）固定。30分コマ（1日48コマ）の開始時刻が属する日を「対象実需給日」とし、コマ48（23:30〜24:00）は当日に帰属する。沖縄エリア（エリアコード 10）は本土と系統連系がなくインバランス制度が異なるため、全入口で登録を拒絶する |

| 3 | 合成単価の禁止と丸めの層別原則 | コマ単位・単価単位の金額丸めは禁止。**生データ層・事実ファクト層では数値を一切丸めない**（欠損補完・0置換・物理上限クリップは値の置換であり丸めではない）。丸めは**集計マート層の月次確定バッチで、請求元約款・法令の方式（精算丸めルールマスタ）に従って1回だけ**適用し、差額は過去レコードを書き換えず「請求丸め調整」列に月末日行として計上する。協定書・法令が丸めを規定する精算結果（BG按分額の1円精算）は規定どおり丸め、未丸め値を併せて保持する |
| 4 | 計画値同時同量の基準統一 | インバランス算出の直前で、需要実績（受電端電力量）を「送電端換算電力量 ＝ 受電端電力量 ÷ (1 − 送電損失率)」で引き直し、計画値（送電端基準）と同じ基準に揃えてから差分を取る |

## 0.3 太陽光・風力の現実現象とデータ特性

| 電源 | 現象 | データ設計への影響 |
|---|---|---|
| 太陽光（SOL） | 日射量に100%依存し、夜間の発電実績は物理的に 0。過積載設備は昼間ピークで横ばい（ピークカット） | 夜間の微小な通信ノイズは**強制的に 0 置換**（補完フラグ1）。物理上限は認可出力×0.5h×1.2 で判定し、超過はビット化けとみなす |
| 風力（WND） | 風速の3乗に比例して出力が変動し不規則なスパイクを起こす。強風時は安全のため自動停止（カットアウト）し突如 0 になる | 前週同曜日コピーによる補完は通用しない。連続欠損は**気象予測連動の計画値**で代替（補完フラグ4）。カットアウトの 0 は異常値ではなく正常として扱う |
| FIP 制度 | JEPX エリア価格で売電（市場売電）し、基準価格（F）と市場参照価格（A：月次加重平均）の差額プレミアムとバランシングコストを不課税の交付金として受け取る | 市場売電はマイナス価格のコマで負の売上になるが、プレミアムは 最大(0, F−A) で 0 クリップし負の交付金にならない。A値は暫定→確定で洗替 |

# 📄 01_architecture_and_master.md（全体構造・マスタ定義詳細）

## 1. アーキテクチャと命名規約

### 1.1 4つの論理データセットと責務分離

| 論理データセット | 接頭辞 | 責務 | 禁止事項 |
|---|---|---|---|
| 生データ層（Bronze） | （なし。データセット `bronze_*` で識別） | 外部・社内ソースから受領したファイル・レコードを**無加工**で保持する。受信メタデータ（ソース名・ファイル名・受信日時・ファイルハッシュ・バッチID）を付与し、受信日で日次パーティションする | 値の変換・名寄せ・欠損補完を行わない。再処理の原本として10年保持 |
| 事実ファクト層（Silver） | `d_`／`f_`／`v_` | 名寄せ・型変換・期間管理を施した「事実」を保持する。マスタは期間管理（SCD Type 2）、ファクトは対象実需給日で日次パーティション。Silver のビューは複数の事実を1本に並べるだけで解釈を加えない | 業務ロジック（休日判定・損益計算）を書かない。**数値を丸めない（税抜化も行わない。公表値・受領値を税区分付きで保持）**。確定層への更新・削除は禁止 |
| 集計マート層（Gold） | `t_`／`mv_` | 日報・月次の損益、インバランス、品質、予測精度を**物理テーブル**として生成する。売上・原価は費目別総額の和として持ち、合成単価を作らない。**税抜化（未丸め）と、月次精算での約款・法令に基づく丸めはこの層でのみ行う** | BI が直接 Silver を参照しない。マートの再生成は対象日パーティション単位のべき等処理に限る |
| 抽出専用ビュー層（Gold ビュー） | `v_` | BI（Looker Studio）の抽出データソース、および休日判定・実量制判定など「解釈」を含む結合を提供する | 抽出用ビューは検算通過行のみを返す。コマ粒度は抽出上限を超えるためライブ接続専用マートを使う |

Silver の `v_` と Gold の `v_` は「事実の統合」と「解釈」の境界であり、名前でどこまでが事実でどこからが判断かを識別できるようにする。

### 1.3 物理配置の共通原則（BigQuery）

| 項目 | 原則 |
|---|---|
| 型 | 金額・電力量は高精度10進数（NUMERIC）。フラグは整数（INT64、0/1）。日付は DATE、時刻は TIMESTAMP（JST 固定）。文字列は STRING |
| パーティション | 大量ファクト・マートは「対象実需給日」で日次パーティション。速報ストリームのみ「取込日」でパーティションし有効期限で自動パージ |
| クラスタ | エリアコードを非正規化保持し、`(エリアコード, 地点番号)` または `(エリアコード, 流向, セグメント, BG)` でクラスタ |
| パーティションフィルタ | すべてのファクト・マートで必須（`require_partition_filter`）。フィルタなしの全件スキャンを構造的に禁止 |
| 主キー | BigQuery の主キー・一意制約は NOT ENFORCED のため、一意性は日次の検算（重複 0 件チェック）で担保する。CHECK 制約は未サポートのため、値域検証はユーザー定義関数をステージング層で強制する |
| 期間管理の結合 | 期間管理マスタへの結合は必ず「対象実需給日 BETWEEN 適用開始日 AND 適用終了日」を付ける。有効レコードの終了日は 9999-12-31 |
| 期間管理キーの安定性 | ファクトが業務識別子を保持するマスタ（BG・BG構成員・発電受給地点・需要家契約履歴・料金メニュー・相対PPA調達契約・登録小売電気事業者・小売事業者エリアコード・休日判定ルール）は、主キーを「業務識別子＋適用開始日」の複合キーとし、改定行の追加時に識別子を変更しない（安定識別子方式）。単価表など識別子を保持しないマスタは版ごとにサロゲートキーを採番し、業務キー＋期間の一意性を検証で担保する（サロゲート方式）。**どのマスタがどちらの方式かをマスタ単位で固定する** |
| 期間列の名前の一意性 | `start_date`／`end_date` は期間管理の適用期間に限って使う。設備の運転開始日など別の意味の日付には使わない（発電所マスタは `operation_start_date`）。混在すると期間重複・隙間の検証を無関係なマスタへ誤って適用する |
| 有効行の終端 | 期間管理マスタの適用終了日は有効行で `9999-12-31`。NULL を使わず、DDL の DEFAULT で統一する |

## 2. 基盤・業務マスタ定義詳細

各マスタは「業務上の意味」「物理仕様」「Fit & Gap」「値の解決アルゴリズム」の順に記述する。

### 2.1 エリアマスタ

**【業務上の意味・背景】**
北海道〜九州の9エリア（沖縄はスコープ外）を社内共通コード（01〜09）で管理し、JEPX・OCCTO・一送の外部コードを名寄せするための対応表。供給地点特定番号の先頭2桁がこのコードと完全に連動するため、地点番号検証の基準表でもある。

**【物理仕様】**

| 論理名 | 物理名 | 型 | 制約 | 備考 |
|---|---|---|---|---|
| エリアコード | `area_code` | STRING | PK | 01〜09 |
| エリア名／一般送配電取引先名 | `area_name` / `ts_company_name` | STRING | NOT NULL | |
| 社内標準略称 | `area_abbr` | STRING | UNIQUE | 画面・帳票用 |
| JEPX 英字表記／OCCTO 英字略称 | `jepx_alpha_code` / `occto_alpha_code` | STRING | UNIQUE | 外部CSVヘッダーの名寄せキー |
| 系統周波数 | `frequency` | INT64 | NOT NULL | 50／60 |
| JEPX 取引対象フラグ | `is_jepx_area` | INT64 | NOT NULL | 9エリアは全て 1 |

**【Fit & Gap（顧客確認事項）】**
・JEPX の CSV 列ヘッダー9件が英字表記と過不足なく一致するか（列が増減した場合は取込を止める）。
・沖縄（10）は登録拒絶で確定。将来沖縄に参入する場合は本マスタとインバランス制度の設計を別途起こす。

**【アルゴリズム】**
生データ層から事実ファクト層へ展開する際、外部コード（英字表記・略称）を本マスタで社内コードに名寄せする。一致しない行は検疫テーブルへ退避し、未名寄せ件数が1件でもあればアラートを出し、日報の公開を止める。

### 2.2 取引先マスタ

**【業務上の意味】** 自社（予約ID `ACCOUNT_SELF`）、顧客（法人・個人）、相対先、BG構成員、発電所の保有者を**1つの取引先（アカウント）として一元管理する**。需要側（電気を売る相手）と発電側（電気を買う相手）の双方が登録され、**顧客とパートナーが混在する**。同一の取引先が「需要家であり、同時に自家発電を売る相手」であることも珍しくないため、役割は単一の区分ではなく需要家／供給者／BG構成員の3フラグで持つ。取引先休日マスタ・BG構成員マスタ・需要家マスタの結合先。**個人需要家も必ず登録し、法人／個人は法人個人区分で区別する**（需要家マスタの取引先IDを NOT NULL にでき、結合が NULL で脱落しないため）。

**【個人情報の扱い】** 取引先名に**個人の氏名を入れない**。本マスタは発電所・BG構成員・相対PPA調達契約から参照され広く読まれるため、氏名を入れると本マスタ全体が PII となり、Policy Tags の付与範囲が参照元へ連鎖する。個人は固定ラベル「個人需要家」を入れ、氏名・住所・連絡先は需要家マスタの PII 列にのみ保持する。

**【物理仕様】** 取引先ID（PK。個人は `IND_` ＋ 需要家ID で採番）、**法人個人区分**（自社／法人／個人）、取引先名、取引先種別（業種の分類。役割は表さない）、**需要家フラグ／供給者フラグ／BG構成員フラグ**（役割。複数 TRUE を許す）、自社フラグ（TRUE は1件のみ）、**登録番号（A番号）**（登録小売電気事業者のみ。登録小売電気事業者マスタへの外部キー。エリアごとの5桁コードは小売事業者エリアコードマスタで解決する）、公的取引先コード、法人番号（法人のみ）。

**【Fit & Gap】** 顧客企業のグループ会社（親子）を1社として扱うか、工場ごとに別取引先にするかは取引先休日の登録単位に影響する。個人取引先の採番規則を業務側と合意する。

**【アルゴリズム】** 自社フラグが TRUE の行が1件であることを検証する。個人取引先は、取引先名に氏名を含まないこと、BG構成員マスタへ登録されないこと、当該需要家1件からのみ参照されることを検証する。役割フラグは参照実態と突合し、参照があるのにフラグが FALSE の行、フラグが TRUE なのに参照が1件もない行を警告する。**需要側・発電側の集計は必ず役割フラグで絞り込み、取引先種別を役割の代用にしない**（買いも売りもする取引先が片方の集計から漏れるため）。

### 2.2b 登録小売電気事業者マスタ／小売事業者エリアコードマスタ

**【業務上の意味】** 電力業界には、管理機関も粒度も異なる**2種類の事業者コード**がある。混同すると届出・電文・スイッチングの識別が破綻するため、親子（1対多）の2マスタに分けて持つ。

| | 登録番号（A番号） | 小売電気事業者コード（5桁） |
|---|---|---|
| 管理機関 | 資源エネルギー庁 | 電力広域的運営推進機関（OCCTO） |
| 粒度 | **1社に全国で1つ**（行政のライセンス管理） | **1社×エリアごとに1つ**（上4桁＝事業者固有、下1桁＝エリア。システム通信・託送識別）。同じ事業者でも販売エリアごとに下1桁が変わる |
| 入手 | 登録小売電気事業者一覧から一括ダウンロード可。法人番号も含む | **一括提供なし**。社内システム・提出控え・取引明細から抽出 |
| 保持先 | 登録小売電気事業者マスタ | 小売事業者エリアコードマスタ |

これに加えて、**一般送配電事業者コード**（託送請求・確報データのファイルヘッダーに入る送信元識別コード）をエリアマスタに保持する。これも一括提供がなく、EDI・ビジネスプロトコル仕様書の巻末マスタ、または受信済みファイルのヘッダーから抽出する。

> **一般送配電事業者コードは小売電気事業者には割り当てられない。** 送配電網を保有する会社に付与されるコードであり、小売は電線を持たないためである。需要家が属する送配電事業者コードは、契約先の小売が誰であってもその地域の一般送配電事業者のものになる。したがって取引先マスタにこのコードの列を作らない。自社を識別するのは登録番号と小売事業者コードである。

**混同しやすい番号**：手続き書類で「10桁の番号」を求められた場合、一般送配電事業者コードではなく、電気を使用する場所を特定する**供給地点特定番号（22桁）**か、**小売事業者が独自に発行するお客様番号**（10桁前後。公的コードではない）を指していることが多い。本基盤は地点の識別に必ず22桁の供給地点特定番号を用い、他社のお客様番号を結合キーにしない。

**【物理仕様（登録小売電気事業者マスタ）】** 登録番号＋適用開始日（複合PK。期間管理）、適用終了日、登録事業者名、法人番号、取引先ID（取引のある事業者のみ）、自社フラグ、登録日／登録取消日、事業者区分、情報ソース／取得日。
**【物理仕様（小売事業者エリアコードマスタ）】** 登録番号＋エリアコード＋適用開始日（複合PK）、適用終了日、小売事業者コード（5桁）、事業者コード（前4桁）、取得元（スイッチング支援システム／供給計画届出書／JEPX取引明細／手動）、情報ソース／取得日。コードはいずれも**先頭ゼロを含む文字列として保持し数値化しない**。

**【Fit & Gap】** 5桁コードと一般送配電事業者コードは一括ダウンロードできないため、初期構築で抽出工数を見込む必要がある。抽出元（下記）のうちどれが自社で参照可能かを事前に確認する。登録取消となった事業者の行を残す方針と、スイッチング履歴をどこまで遡って解決するか。

**【アルゴリズム（初期データの作成手順）】**

```
Step 1  登録番号（A番号）の土台を作る
        資源エネルギー庁の登録小売電気事業者一覧をダウンロード
        → 自社の商号で検索し、登録番号と法人番号を抽出して登録小売電気事業者マスタへ投入
        → 取引のある他社（スイッチング相手先、相対先、BG構成員）も同一覧から投入

Step 2  小売事業者コード（5桁）を紐付ける ※一括提供なし
        方法A：OCCTO スイッチング支援システム、またはBGマスタ設定画面から
               自社の事業者コード（前4桁）と進出エリア（末尾1桁）の組合せを確認
        方法B：供給計画届出書（提出支援ツールの内部マスタ、過去の提出控え）から抽出
        方法C：JEPX の取引結果・請求電文に含まれる取引主体コードから逆引き
        → 進出エリア分を小売事業者エリアコードマスタへ投入（取得元を記録）

Step 3  一般送配電事業者コードを紐付ける ※一括提供なし
        方法A：各一送の EDI・ビジネスプロトコル仕様書の巻末マスタ（コード定義章）
        方法B：受信済みの託送請求データ・確報データのファイルヘッダー（先頭行）
        → エリアマスタへ投入

Step 4  検証
        5桁コードの先頭4桁が同一事業者内で一貫していること
        5桁コードの下1桁がエリアマスタのOCCTOエリア数字（北海道1〜九州9）と一致していること
        自社フラグが有効期間内に1件のみであること
        期間の重複・隙間がないこと
```

**【運用】** 自社の届出・電文には**エリアごとの5桁コード**を用いる。設定値に埋め込まず「自社フラグが TRUE の登録事業者 × 対象エリア」で解決する。切替電文の相手先5桁コードは、小売事業者エリアコードマスタ → 登録小売電気事業者マスタの順に解決して事業者名・取引先へ名寄せし、未登録コードは検疫して未名寄せとしてアラートする。

### 2.3 送電損失率マスタ

**【業務上の意味・背景】**
一送約款に定める送電損失率を、エリア×電圧クラス別に期間管理で保持する。需要実績（受電端）を送電端に換算するための唯一の根拠であり、インバランス算定・電力量突合・市場原価按分のすべてに影響する。

**【物理仕様】**

| 論理名 | 物理名 | 型 | 制約 |
|---|---|---|---|
| 損失率ID | `loss_rate_id` | INT64 | PK |
| エリアコード／電圧クラス | `area_code` / `voltage_class` | STRING | NOT NULL |
| 送電損失率 | `loss_rate` | NUMERIC | NOT NULL（0 以上 0.2 未満） |
| 適用開始日／終了日 | `start_date` / `end_date` | DATE | NOT NULL |

**【Fit & Gap】** 各一送の約款別表の損失率（電圧クラス別）。レベニューキャップ制度の改定サイクルに合わせて新レコードを追加する。約款が「損失率を乗じる」か「損失率で除す」かの表現差（R-22）。
**【アルゴリズム】** 送電端換算電力量 ＝ 受電端電力量 ÷ (1 − 送電損失率)。対象実需給日で期間解決し、引けない場合は 0 で埋めず NULL として検算で検知する（日報バッチの前提チェックで強制停止）。

### 2.4 託送料金マスタ（季節別時間帯別と一律従量の同列管理）

**【業務上の意味・背景】**
託送料金は「基本料金（円/kW・月）」と「電力量料金（円/kWh）」で構成され、低圧は一律の従量単価、高圧・特高は「季節（夏季／その他季）×曜日（平日／休日）×時間帯（昼間／夜間／ピーク）」の3次元で従量単価が変動する約款が一般的である。 では、一律メニューと時間帯別メニューを**1つのマスタで横持ち**し、時間帯別列が空の場合は標準単価へ自動フォールバックさせることで、電圧クラスごとに単価解決の SQL を分けない。

**【物理仕様】**

| 論理名 | 物理名 | 型 | 制約 | 備考 |
|---|---|---|---|---|
| 託送料金ID | `wheeling_rate_id` | INT64 | PK | |
| エリアコード／電圧クラス | `area_code` / `voltage_class` | STRING | NOT NULL | |
| メニュー名／既定メニューフラグ | `menu_name` / `is_default` | STRING / INT64 | NOT NULL | 同一エリア×電圧×期間で既定は1行 |
| 需要側 基本料金単価 | `demand_fixed_rate` | NUMERIC | NOT NULL | 円/kW・月 |
| 需要側 電力量料金単価（標準） | `demand_variable_rate` | NUMERIC | NOT NULL | 一律メニューの従量単価、または時間帯別メニューの「その他季昼間」 |
| 夏季昼間／夏季ピーク／冬季昼間／夜間 単価 | `variable_rate_summer_day` / `variable_rate_summer_peak` / `variable_rate_winter_day` / `variable_rate_night` | NUMERIC | NULL可 | 一律メニューは NULL |
| 発電側 課金単価／従量課金単価 | `gen_charge_rate` / `gen_charge_kwh_rate` | NUMERIC | NOT NULL / NULL可 | 円/kW・月 ／ 円/kWh |
| 税区分 | `tax_type` | STRING | NOT NULL | 税抜固定 |
| 適用開始日／終了日 | `start_date` / `end_date` | DATE | NOT NULL | |

**【Fit & Gap（顧客確認事項）】**

| 確認事項 | 影響 |
|---|---|
| 冬季昼間の特掲単価の有無 | ある一送のみ冬季昼間列を登録。なければ空欄で「その他季昼間」へフォールバック |
| 発電側課金の割引条件・単価 | 割引対象の判定条件（既設電源の激変緩和等）と単価そのものは一次情報で確認する |
| 休日の昼間に適用する単価（その他季昼間か、夜間か） | 標準実装は「その他季昼間」。約款が異なる場合は休日判定ルールマスタの託送用ルールで切り替える |
| 夏季・冬季の境界月（7〜9月／12〜2月が標準） | 日付カレンダーマスタの電力季節列の定義で吸収 |
| 同一エリア×電圧に複数メニューがある場合の需要家ごとの選択 | 需要家契約履歴マスタの託送メニュー名で指定。未指定は既定メニュー |

**【アルゴリズム（単価解決）】**
入力：対象実需給日、コマ番号、エリア、電圧クラス、契約の託送メニュー名。出力：適用託送従量単価。
1. 需要家契約履歴マスタの託送メニュー名が指定されていればそのメニュー、なければ既定メニューの行を対象実需給日で期間解決する。
2. 次の優先順位で単価を決める（上から最初に該当したもの）。
   - コマの時間帯区分が「夜間」 → 夜間単価（空なら標準単価）
   - 料金上の休日（自社の約款休日を最優先、なければ土日祝） → 標準単価
   - 電力季節が「夏季」かつコマがピーク → 夏季ピーク単価（空なら標準単価）
   - 電力季節が「夏季」 → 夏季昼間単価（空なら標準単価）
   - 電力季節が「冬季」 → 冬季昼間単価（空なら標準単価）
   - それ以外 → 標準単価
3. 標準単価が引けない行は NULL とし、日報バッチの前提チェックで強制停止する。

### 2.4b アンペア料金マスタ

**【業務上の意味】** 低圧従量電灯の主流であるアンペア制契約（10A〜60A）の基本料金は、契約電力(kW)ではなく契約アンペアで決まる固定額（円/月）である。小売（自社料金メニュー）と託送（一送約款）それぞれのアンペア別金額を、エリア×料金メニュー×アンペアで保持する。
**【物理仕様】** アンペア料金ID（PK）、料金メニューコード、エリアコード、契約アンペア(A)、小売基本料金（円/月・税抜）、託送基本料金（円/月・税抜）、適用開始日／終了日。
**【Fit & Gap】** 小売・託送は別々の管理主体・改定サイクルを持つため、本来は別テーブルが自然だが実装簡略化のため1テーブルに同居させている。改定タイミングがずれる場合はテーブルを分割する。
**【アルゴリズム】** 契約に契約アンペアが設定されている場合、当該アンペアの固定額を月日数×48で日割りし、`rev_base_est`／`cost_wheeling_fixed_est` に直接計上する（kW×単価の計算はバイパスする）。契約電力(kW)と契約アンペアはどちらか一方のみを持ち、電圧クラスは低圧、実量制フラグは0であることを登録時に検証する。

### 2.5 燃料費調整単価マスタ

**【業務上の意味】** 固定単価メニューの電力量料金に加算する、エリア×電圧クラス×対象年月の公表単価。市場連動メニューには適用しない（二重計上禁止）。
**【物理仕様】** 燃調ID（PK）、エリアコード、電圧クラス、対象年月（YYYYMM）、燃料費調整単価（**公表値のまま・未丸め**）、離島調整単価、上限適用フラグ、公表元、公表日、公表時の税区分（税込／税抜）。
**【Fit & Gap】** 公表元（旧一電）が税込で公表する場合と税抜の場合が混在する。事実ファクト層では換算せず公表値と税区分をそのまま保持し、集計マート層で税抜化する。
**【アルゴリズム】** 日報バッチで「対象実需給日の年月 ＝ 対象年月」で結合し、公表時の税区分が税込なら「単価 ÷ (1＋消費税率)」を未丸めで税抜化する。料金メニューマスタの燃調適用フラグ＝1 の場合のみ「需要実績量（受電端）× 税抜燃料費調整単価」を売上内訳（燃料費調整額）に計上する。翌月分が公表期限までに未登録ならアラート。

### 2.6 容量拠出金マスタ

**【業務上の意味】** 容量市場の拠出金を、年度×エリアの一律 kWh 単価で調達原価に按分する（確定）。ピーク時 kW 按分は列のみ予備で保持し使用しない。
**【物理仕様】** 容量拠出金ID（PK）、エリアコード、年度、一律kWh単価（税抜）、ピーク時kW単価（予備）、適用開始日／終了日。
**【Fit & Gap】** 実際の請求方式（一律 kWh か、ピーク時 kW 按分か）は制度・約款で確認（R-6）。
**【アルゴリズム】** 調達原価内訳（容量拠出金）＝ 需要実績量（受電端）× 一律kWh単価。対象実需給日で期間解決。

### 2.6b 発電側課金割引率マスタ

**【業務上の意味】** 2024年度に導入された、発電事業者にも送配電網の維持費を負担させる制度（発電側課金）の割引率を、エリア×割引区分で期間管理する。単価そのもの（円/kW・月、円/kWh）は託送料金マスタ（2.4）の発電側課金単価列を流用する。
**【物理仕様】** 割引率ID（PK）、エリアコード、発電側課金区分、割引率、適用開始日／終了日。
**【Fit & Gap】** 割引の対象条件（既設電源の激変緩和等）と単価そのものは一次情報で確認する。
**【アルゴリズム】** 発電受給地点の契約出力(kW) × 発電側課金単価 × (1−割引率) を月割りし、発電実績量×従量課金単価（制度上あれば）を加算して、発電行の調達原価に計上する。

### 2.7 再エネ賦課金マスタ

**【業務上の意味・背景】**
国が年度ごとに公表する一意の税込単価。需要家への請求は「検針月」基準（毎年5月検針分から新単価）で決まるため、対象実需給日ではなく検針サイクルマスタの請求月で解決する。単価を税抜化せず**税込のまま**保持する。

**【物理仕様】** 賦課金ID（PK）、年度、賦課金単価（税込）、適用基準（検針月）、適用開始請求月／終了請求月。
**【Fit & Gap】** 請求システムの賦課金計算順序（税込月合算 → 切捨て → 税抜化）と丸め方式（切捨てが標準）を精算丸めルールマスタに登録すること。
**【アルゴリズム】**
1. 需要地点 × 対象実需給日 → 検針サイクルマスタで請求月を解決。
2. 請求月 → 本マスタで税込単価を解決。
3. 日次：賦課金（税込総額）＝ 需要実績量（受電端）× 税込単価（未丸め）。参考値として税抜換算（÷(1＋税率)、未丸め）も併記。
4. 月次：需要家×請求月で税込総額を合算 → 精算丸めルールの方式で1円単位に丸め → 税抜化。日次参考値との差を請求丸め調整に計上。

### 2.8 FIP バランシングコストマスタ

**【業務上の意味】** FIP 発電所に対する調整費用（バランシングコスト）と、激変緩和の上乗せ（一定年度で終了）を、認定年度×実需給年度×電源種別×エリアの4軸で持つ。上乗せ終了年度以降は上乗せ＝0 を明示登録して自動消失させる。
**【物理仕様】** 認定年度、実需給年度、電源種別コード、エリアコード（4軸で複合PK）、基礎バランシングコスト、激変緩和上乗せ、合計バランシングプレミアム、公表元、公表日。
**【Fit & Gap】** 年度・単価の公表値（R-24）。認定年度は発電受給地点マスタの FIP 認定年度から解決する。
**【アルゴリズム】** 発電売上内訳（バランシングコスト）＝ 発電実績量 × 合計プレミアム（不課税）。FIP プレミアム ＝ 発電実績量 × 最大(0, 基準価格F − 参照価格A)。

### 2.9 JEPX 取引手数料マスタ

**【業務上の意味】** 取引手数料（0.03円/kWh）と決済代行手数料（0.01円/kWh）を売買区分別・従量で、年会費・システム利用料を定額で持つ。従量分は約定明細取込時に確定し、定額分は前月実績ベースの暫定単価で日次計上して月次で精算する。
**【物理仕様】** 手数料ID（PK）、市場種別、手数料種別、課金方式（従量／月額定額）、売買区分、単価、税区分、支払先、適用開始日／終了日。
**【Fit & Gap】** JEPX 規程の手数料改定（R-15）。定額の按分基準（前月総約定量）は社内ルール。
**【アルゴリズム】** 従量：約定量 × (取引＋決済代行)。定額暫定：当日約定量（買）× (前月定額総額 ÷ 前月総約定量)。月次確定差額は月末日行に一括計上。

### 2.10 需要家マスタ（システム結合列と個人識別情報の物理分離）

**【業務上の意味・背景】**
需要家（契約者）と需要地点（22桁の供給地点特定番号）を1対1で管理する基幹マスタ。日報バッチ・BI・実量制判定が頻繁に結合する「契約・場所属性」と、個人情報保護規程上の閲覧制限対象となる「氏名・住所・連絡先」を、**列名の接頭辞（`pii_`）で物理的に分離**する。これにより、将来 BigQuery の Policy Tags（列レベルアクセス制御）へ移行する際に、スキーマ変更・ビュー書換え・バッチ改修を一切行わず、タグ付与のみで閲覧制限を掛けられる。日報バッチと BI は個人識別情報列を参照しないため、スキャン量も抑えられる。

**【物理仕様】**

| 区分 | 論理名 | 物理名 | 型 | 制約 |
|---|---|---|---|---|
| 結合キー | 需要家ID | `customer_id` | STRING | PK |
| 結合キー | 需要地点番号 | `demand_point_number` | STRING | UNIQUE。先頭3桁検証を通過したもののみ |
| 結合キー | 取引先ID | `account_id` | STRING | FK。**NOT NULL**（個人も取引先を登録する） |
| 結合キー | エリアコード／電圧クラス | `area_code` / `voltage_class` | STRING | NOT NULL。電圧クラスは 低圧／高圧／特高 |
| 結合キー | 需要種別／実量制フラグ | `customer_type` / `is_actual_kw_based` | STRING / INT64 | |
| 結合キー | 作成／更新日時 | `created_at` / `updated_at` | TIMESTAMP | |
| PII | 需要家名 | `pii_customer_name` | STRING | NOT NULL。Policy Tags 対象 |
| PII | 郵便番号／都道府県／住所1／住所2 | `pii_postal_code` / `pii_prefecture` / `pii_address_line1` / `pii_address_line2` | STRING | Policy Tags 対象 |
| PII | 電話番号／メールアドレス | `pii_phone_number` / `pii_email` | STRING | Policy Tags 対象 |

クラスタ：エリアコード、電圧クラス、需要家ID。

**【Fit & Gap】**
・初期構築はマスキングなし（生データ保持）で確定。閲覧制限が必要になった時点で Policy Tags を付与する。
・都道府県を分析軸（エリア内の地域差）として使う場合は、PII 側から非 PII 側へ列を分離してよい。
・法人需要家のグループ企業をどの取引先IDに紐付けるかは、取引先休日・BG構成員の登録単位と整合させる。

**【アルゴリズム（登録ゲート）】**
1. 需要地点番号は「22桁の半角数字」「先頭2桁が 01〜09（沖縄 10 は拒絶）」「先頭2桁 ＝ エリアコード」「3桁目が 低圧＝0／高圧・特高＝1」をユーザー定義関数で検証し、OK 以外は登録・移行を拒否する（03-7）。
2. BigQuery は CHECK 制約を持たないため、検証はテーブル定義ではなく、Bronze→Silver 展開・移行スクリプト・マスタ更新手続きの**共通ゲート**として強制する。

### 2.11 需要家契約履歴マスタ（期間管理）

**【業務上の意味】** 需要家のプラン変更・BG乗換・契約電力変更を、適用開始日／終了日の履歴（SCD Type 2）で保持する。日報バッチは対象実需給日で有効な1行を解決する。

**【アルゴリズム】** 料金メニューマスタの環境価値種別が「なし」以外の需要家について、証書種別＝メニューの環境価値種別、対象年度＝実需給年度、対象実需給日で期間解決した単価を「需要実績量（受電端）× 証書単価」で調達原価（非化石証書）に計上する。単価が引けない場合は 0 ではなく NULL とし、検算で検知する。月次で「証書種別・年度別の需要実績量 ≤ 購入量」を検算し、不足はアラート。

### 3.3 汎用休日マスタ／取引先休日マスタ

**【業務上の意味・背景】**
汎用休日マスタは、デジタル庁が配信する祝日CSVを**唯一のソース**とする祝日と、生成バッチが自動投入する土日を1テーブルで持つ（休日判定を左外部結合1本で済ませるため）。取引先休日マスタは自社と顧客企業の取引先休日を取引先IDで一元管理し、自社の約款休日（料金適用フラグ＝1）は供給約款上「当社が定める休日」として**曜日・祝日に関わらず最優先**で休日単価を適用する。顧客企業の休日は需要予測の特徴量（想定稼働率）にのみ使い、料金には影響させない。

**【物理仕様（汎用休日）】** 休日日付（PK）、休日区分（国民の祝日／振替休日／国民の休日／臨時／取消／土曜／日曜／年末年始／大型連休特定日）、休日名称、国民の祝日フラグ、情報ソース、登録日、備考。
**【物理仕様（取引先休日）】** 取引先ID＋取引先休日日付＋適用需要地点（NULL＝全地点）、休日理由、休日区分、想定稼働率（平常日＝1.00）、料金適用フラグ、情報ソース、登録日／更新日時。
**【Fit & Gap】** 自社約款の「当社が定める休日」の具体日（年末年始・お盆・創立記念日）。顧客企業の休日登録の責任者とエスカレーション（業務側で定義：Q-13）。
**【アルゴリズム（料金用休日判定）】**
1. 自社（`ACCOUNT_SELF`）・全地点・料金適用フラグ＝1 の取引先休日に該当 → 料金上の休日。
2. そうでなければ、汎用休日マスタで土日祝（取消を除く）に該当 → 料金上の休日。
3. それ以外 → 平日。
祝日CSVの取込（B-10）はフォーマット変更に備えたフェイルセーフを持つ（04-3）。

## 4. マスタデータ移行（データクレンジング）手順

**【業務上の意味・背景】**
他社・レガシーシステムから契約履歴を移行すると、「同じ日に複数プランが有効」（期間の重複）や「数日間の未契約」（期間の隙間）が高確率で混入する。重複は日報バッチで行が増殖して売上が二重計上され、隙間は単価が引けず日報が停止する。移行フェーズの前段、および本番のマスタ更新手続きの前段で、**重複・隙間・開始終了逆転を1本の検証 SQL で検出し、エラーがあれば登録を拒否**する。

**【検証仕様】**

| 判定 | 条件 | 結果 |
|---|---|---|
| 開始終了の逆転 | 適用開始日 ＞ 適用終了日 | エラー（拒否） |
| 期間の重複 | 同一キー内で、次レコードの開始日 ≤ 自レコードの終了日 | エラー（拒否） |
| 期間の隙間 | 終了日が永続（9999-12-31）でなく、終了日＋1日 ≠ 次レコードの開始日 | 契約履歴：エラー（拒否）／単価マスタ：警告 |
| 最新レコードが閉じている | 終了日が永続でなく次レコードが無い | 警告（解約済みなら正常） |

検証の単位（同一キー）は「同一時点に1行しか有効であってはならないキー」に合わせる。需要家契約履歴は需要家ID、単価マスタはエリア×電圧クラス（×メニュー名）。並行契約を許すキーで実行すると正常な履歴を重複と誤検知する。永続レコードの終了日は日付リテラルで比較し、日付加算の範囲外エラーを避ける。

**【是正の運用フロー】**

```
1. 抽出   レガシーから契約履歴を抽出 → ステージング表へ
2. 検証   重複・隙間・逆転の検証 SQL を実行 → 検疫レポート（需要家ID／エラー種別／該当履歴ID）
3. 是正   重複：受付日時が新しい（改訂版が大きい）レコードを優先し、
          古いレコードの終了日を「新レコードの開始日 − 1日」へ縮退
          隙間：数日なら前レコードの終了日を延長。真の無契約期間は
          専用メニュー（従量・基本料金 0、インバランスは原価側へ 100%）を挿入
          ※ 縮退・延長・挿入はすべてマスタ変更監査ログに旧値・新値・理由を記録
4. 再検証 エラー 0 件になるまで 2〜3 を反復
5. 投入   事実ファクト層へ MERGE。本番のマスタ更新手続きでは同じ検証をゲートに組み込み、
          エラー 1 件以上で処理をロールバックして登録を拒否
```

**【Fit & Gap】** 解約→再契約の間の無契約期間を「隙間として埋める」か「専用メニューで明示する」かは業務判断（請求・インバランス負担の扱いが変わる）。

## 1. 需要・発電実績の3層物理分割原則

**【業務上の意味・背景】**
実績データは、①当日の需給監視のために数分間隔で追記される速報、②翌朝一括で UPSERT される日次確報、③翌月20日頃に一送から届き顧客請求・公的精算に使う月次確定、と更新ライフサイクルが根本的に異なる。1テーブルに混ぜると、数千万件規模のコマデータへの高頻度 UPDATE が日報の表示性能を落とし、決算・請求に使った確定値が日々の更新の巻き添えで書き換わる事故を防げない。したがって実績だけは**物理的に3テーブルに分割**する。

| 層 | 更新方式 | 用途 | 保持 |
|---|---|---|---|
| 速報ストリーム | 追記のみ（5〜30分間隔）。再送を含む | 需給逼迫監視・当日判断 | 7日（取込日パーティションの有効期限で自動パージ） |
| 速報最新行キャッシュ | 数分間隔のマイクロバッチで「地点×日×コマ」の最新行を UPSERT | 統合ビューと速報モニタの参照先 | **直近7日** |
| 日次確報 | 翌朝 06:00 に取得→クレンジング→UPSERT | 経営日報・粗利分析 | 13ヶ月（確定で置き換わる） |
| 月次確定 | 翌月 21日頃に一括 INSERT。**UPDATE／DELETE 禁止** | 顧客請求・公的精算・監査 | 10年（本番上、長期保存料金） |

**【物理仕様】**

| 論理名 | 物理名 | パーティション | クラスタ | 備考 |
|---|---|---|---|---|
| 需要実績（速報）／（確報）／（確定） | `fact_dem_actuals_stream` / `fact_dem_actuals_daily` / `fact_dem_actuals_settled` | 速報：取込日、確報・確定：対象実需給日 | エリアコード、需要地点番号 | 主キー：需要地点番号×対象実需給日×コマ番号（速報は取込日時を含む） |
| 発電実績（速報）／（確報）／（確定） | `fact_gen_actuals_stream` / `fact_gen_actuals_daily` / `fact_gen_actuals_settled` | 同上 | エリアコード、発電受給地点番号 | 同上 |

> **試運転（コミッショニング）期間**：系統連系後、商業運転開始日（COD）までの期間も系統へ電気が流れる。発電受給地点マスタに**試運転開始日・商業運転開始日・試運転中の売電計上区分**を持ち、期間中は (1) 実績を補完せず生値のまま保持（補完フラグ 7）、(2) 市場売電は地点ごとの設定で計上を切り替え、(3) FIP交付金は商業運転開始日以降に限定、(4) 発電側課金は課金起算基準（系統連系日／COD）で切り替える、(5) インバランスは除外しない（同時同量の対象）、(6) 計画精度の監視からは除外する。出力抑制試験・解列試験で意図的に出力をゼロや急変させるため、通常のクレンジングをかけると実態と乖離する。売電計上の可否と日付の取得元は導入前に業務部門と合意する（設計仕様書 17.4 A-1〜A-4）。
| 速報最新行キャッシュ（需要／発電） | `fact_dem_actuals_stream_latest` / `fact_gen_actuals_stream_latest` | 対象実需給日（有効期限 7日） | エリアコード | 実績値、元の取込日時、更新日時 |

**【Fit & Gap】** 一送のスマートメーター速報の再送頻度と遅延（速報の有効期限7日で足りるか）。確報の到着時刻（06:00 前提）。

## 2. 実績3層時系列統合ビューの設計

### 2.1 目的と構造

利用者には3層を意識させず、Silver の統合ビュー（需要実績時系列統合ビュー／発電実績時系列統合ビュー）が「確定 → 確報 → 速報」の優先で1本の時系列を返す。各行は「データ状態（確定値／確報値／速報値）」を持ち、BI と日報バッチはこれを見て数字の成熟度を表示・判定する。

### 2.2 3層の境界判定（動的補完結合ロジック）

**【業務上の意味・背景】**
確報バッチ（B-04）は翌朝 06:00 に走るため、例えば 9月9日 02:00 の時点では 9月8日分が「確報にはまだ無く、速報層の条件（今日）にも該当しない」状態となり、**前日48コマがビューから丸ごと消えて**いた。 では速報層を「直近7日のうち確報に存在しないコマ」に広げ、確報が到着した瞬間に自然に確報値へ切り替わる（同一コマの二重計上は起きない）。

**【アルゴリズム】**

```
入力：月次確定、日次確報、速報最新行キャッシュ、確定値受領状況
出力：需要地点番号 × 対象実需給日 × コマ番号 × 実績値 × データ状態

① 確定層   確定値受領状況で「当該エリア×当該月×需要側 の受領完了 ＝ 1」の月
            訂正は打ち消しレコードの追記で行われるため、地点×日×コマで合算して1行にする
            → データ状態「確定値」
② 確報層   対象実需給日 ＜ 今日 かつ 当該月の確定値が未受領
            → データ状態「確報値」
③ 速報層   対象実需給日 が 今日−7日 〜 今日（静的なパーティション絞り込み）
            かつ（対象実需給日 ＝ 今日 または 同一 地点×日×コマ の行が日次確報に存在しない）
            かつ 当該月の確定値が未受領
            → データ状態「速報値」
①∪②∪③ を UNION ALL
```

| 設計上の規定 | 内容 |
|---|---|
| 境界は受領状況テーブルで動的判定 | 固定の月初判定を使わない。確定値の受領が遅れた月は確報層を見続け、受領完了（件数一致）で初めて確定層へ切り替わる |
| 速報層の相関サブクエリ | 両側を対象実需給日でパーティション絞り込みするため、走査は「直近7日×地点×48コマ」に限定される |
| ビュー内でウィンドウ関数を掛けない | 速報ストリーム本体は日に数千万〜数億行になる。最新行の抽出はマイクロバッチで速報最新行キャッシュに書き出し、ビューはそれを読むだけにする |
| 発電側 | キー名と受領状況の「側」だけが異なる対称構造 |

**【Fit & Gap】** 確報が 06:00 より遅れる一送がある場合、速報層の窓（7日）は変更不要だが、日報バッチの開始時刻（07:00）と SLA を見直す。

### 2.3 速報最新行キャッシュの配置

| 項目 | 内容 |
|---|---|
| 更新 | 5〜15分間隔のマイクロバッチ。速報ストリームの「取込日時 ≥ 現在−2時間」の追記分から地点×日×コマの最新行を抽出し UPSERT（静的な絞り込みを必ず入れる） |
| 保持 | 直近7日。統合ビューが確報未展開の過去日を補完するために必要 |
| 参照 | 統合ビュー、速報モニタ（マテリアライズドビュー）。ストリーム本体は BI から読まない |

### 2.4 確報層のクレンジングと自動補完（電源特性別）

**【業務上の意味】** 日次確報は経営日報の基礎であり、欠損・異常値を放置すると粗利が歪む。補完はルール化し、補完したコマには補完フラグを付けて追跡可能にする（補完率は月次KPI）。

| ケース | 判定 | 補完方法 | フラグ |
|---|---|---|---|
| マイナス値（逆潮流なし・発電の待機電力） | 実績 ＜ 0 | 0 に置換 | 1 |
| 太陽光の夜間 | 月別の夜間時間帯（日射量データがあればそれを優先）に欠損またはプラスの異常値 | 前週コピーを行わず**強制的に 0** | 1 |
| 単発（1〜2コマ）の欠損・異常 | — | 前後コマの線形補完 | 2 |
| 物理限界超過 | 実績 ＞ 認可出力 × 0.5h × 1.2 | 線形補完、または認可出力 × 0.5h でクリップ | 2 |
| 連続欠損（需要側・常時稼働電源） | — | 前週同曜日の同時刻をコピー（休日属性を合わせる） | 3 |
| 連続欠損（太陽光・風力） | 前週コピーは気象条件が異なり不適 | 前日同時刻、または気象予測ベースの計画値で代替。風力のカットアウト（強風停止）の 0 は正常値として補完しない | 3／4 |
| 訪問検針地点（30分値なし） | 検針区分＝訪問検針 | 月間総量を標準負荷プロファイルで48コマへ配分（補完ではなく配分） | 5 |
| 一送の推定検針 | 検針区分＝一送推定 | 値を変更せずフラグのみ付与。分析から除外できるようにする | 6 |
| **試運転期間中の発電実績** | 試運転開始日 ≤ 対象日 ＜ 商業運転開始日 | **補完を一切行わず生値のまま保持**。出力抑制試験・解列試験のゼロや急変を欠測・カットアウトと誤判定しないため | 7 |

1日のうち補完コマ数が閾値（例：48コマ中6コマ）を超えた地点は日報にアラートを立て、一送へ照会する。

## 3. 市場・計画・BG精算ファクト定義詳細

### 3.2 JEPXスポット価格ファクト／JEPX約定明細ファクト

**【Fit & Gap】** 時間前市場の約定を同一テーブルで持つか（市場種別で区別）。
**【アルゴリズム】** 日報バッチは対象実需給日×コマ×エリア×BGで約定代金と手数料を合算し、BG内の送電端需要比でセグメントへ按分する（03-1）。

### 3.2b JEPX時間前価格ファクト

**【業務上の意味】** 時間前市場（実需給1時間前まで）の加重平均約定価格・約定量・最終約定価格をエリア×対象実需給日×コマで保持する。当日調達の原価参照と、スポット価格との乖離分析（需給逼迫の兆候）に使う。
**【物理仕様】** ID（PK）、対象実需給日＋コマ番号＋エリアコード（複合UK）、加重平均約定価格、約定量、最終約定価格。パーティション：対象実需給日。
**【Fit & Gap】** 時間前の自社約定を約定明細ファクトに市場種別で持つか。
**【アルゴリズム】** 約定明細の市場種別＝時間前の約定は約定代金で原価計上する（価格ファクトは参照・分析用）。

### 3.3 インバランス料金単価ファクト

**【業務上の意味】** エリア×対象実需給日×コマの単価（税抜）。暫定（当日〜翌日）と確定（翌月）があり、更正が届いた場合は**単価を上書きして影響日をリラン**する（版管理・差額調整は行わない）。
**【物理仕様】** 対象実需給日＋コマ番号＋エリアコード（複合PK）、インバランス単価、単価ステータス（暫定／確定）、更新日時。
**【Fit & Gap】** 更正の通知形式。上書き方式で監査要件を満たすか（更正履歴は生データ層に残る）。
**【アルゴリズム】** BG精算額 ＝ BGネットインバランス量 × 単価。更正時は影響日の日報損益・インバランス日次・BG構成員別インバランス・BG月次精算を再計算する。

### 3.4 FIP参照価格（A値）ファクト

**【業務上の意味】** 電源種別×エリア×対象月の参照価格。月中は暫定（市場価格の加重平均）で日次計上し、GIO 公表の確定値で翌月洗替する。
**【物理仕様】** 対象月＋電源種別コード＋エリアコード＋値ステータス（暫定／確定）、参照価格、公表元、登録日時。
**【Fit & Gap】** 確定A値の公表タイミング（毎月25日頃）とリラン範囲。
**【アルゴリズム】** 日報バッチは同一キーに確定があれば確定、なければ暫定を採る（優先順位付き最新1行）。確定取込後に当月分のFIP収支をリランする。

### 3.4b 相対・PPA精算明細ファクト／電力先物価格ファクト／非化石証書購入ファクト

| ファクト | 業務上の意味 | 物理仕様（主要列） | アルゴリズム |
|---|---|---|---|
| 相対・PPA精算明細 | 調達契約ごとの受渡量と精算額（暫定＝自社計算／確定＝相手先通知）。バーチャル PPA は差金が単価に入る | 精算ID（PK）、調達契約ID、対象実需給日、コマ番号、エリアコード、受渡量(kWh)、適用単価、精算金額（**受領値のまま・未丸め**）、データ区分。パーティション：対象実需給日 | 受領時税区分が税込なら日報バッチで「÷(1＋税率)」を未丸めで税抜化。エリア単位で合算 → 送電端需要比でセグメントへ按分（調達原価：相対・PPA・先物）。確定通知との差異が閾値超なら検算アラート |

### 3.5 発電計画ファクト／需要計画ファクト

**【業務上の意味】** 30分コマ単位の計画値(kW)。前日計画（DA）と当日計画（ID）、改訂版を上書きせず履歴保持する。**計画値の基準**（送電端＝OCCTO提出値／受電端＝予測モデルの生値）を明示的に持ち、精算対象の計画（GC確定）は必ず送電端基準とする。

**【Fit & Gap】** 自社が構成員のBGでは自社行のみを持ち、代表者通知額を取り込んで突合する。
**【アルゴリズム】** 03-3。

### 3.7 マスタ変更監査ログ

**【業務上の意味】** 期間管理マスタの変更（追加・更新・縮退・取消）を、変更前後の値を半構造化 JSON で記録する。承認ワークフロー経由の変更のみを許可し、移行時の重複・隙間是正もここに残す。

**【Fit & Gap】** 監査ログの保持期間と参照権限（Q-10）。
**【アルゴリズム】** マスタ更新手続きが変更前後をスナップショットして1行挿入する。手動 UPDATE は権限で禁止。

## 1. 日報損益マート生成コアバッチのロジック詳細仕様

### 1.1 業務上の意味・背景

日報損益マートは、対象実需給日 × コマ × エリア × BG × **流向** × セグメント × メニュー種別の粒度で、売上・調達原価・粗利を1円単位で整合させる最重要マート。毎朝 07:00（前日確報の取込完了後）に生成し、経営日報（P1／P2）の抽出データソース、月次経営サマリ、検算の入力となる。売上・原価は**費目別の総額列の和**として持ち、合成単価を作らない。

### 1.2 物理仕様

### 1.3 主キーへの「流向」内包による衝突回避

セグメントは需要行では電圧クラス、発電行では「発電」と、行の種類ごとに値のドメインが異なる列である。 では**流向**を主キーの第5軸として明示し、需要側の書込は INBOUND、発電側は OUTBOUND を固定で書く。行の種類の判定（粗利更新・検算）もセグメントではなく流向で行う。流向×セグメント×メニュー種別の組合せは登録時に検証し、主キー重複 0 件を検算の前段で確認する。

### 1.4 Fit & Gap

| 確認事項 | 影響 |
|---|---|
| 市場調達原価をセグメントへ按分するキー（送電端需要比で確定） | 契約 kW 比などに変える場合は按分 CTE の分母のみ変更 |
| 基本料金の日割試算（月日数÷48）の扱い | 月次確定で最大kW比に置き換えるため日次は試算値でよいか |
| 発電側課金の扱い（現時点 0） | 制度確定時に発電行の原価へ加算 |

### 1.5 アルゴリズム

**入力**：日次確報（需要・発電）、計画、JEPXスポット価格、約定明細、インバランス単価、相対・PPA精算明細、先物清算値、各マスタ（対象実需給日で期間解決）。
**出力**：日報損益マート（対象日パーティション）、インバランス日次マート、データ品質日次、需要予測精度日次。
**べき等性**：対象日パーティションを削除して再作成する。参照する単価はすべて対象実需給日で期間解決し、実行日時に依存する値を使わない。

```
STEP 0  前提チェック（ガード節。NG なら中断し、中途半端な日報を出さない）
        0-1 需要実績が地点ごとに48コマ揃っているか → 欠番地点数 > 0 なら強制停止・アラート
        0-2 対象日の単価がすべて引けるか（損失率・託送標準単価・JEPX価格・容量拠出金・検針月・賦課金）
            → 単価 NULL 行数 > 0 なら強制停止・アラート（0 で埋めない）
STEP 1  べき等性：日報損益マートの対象日パーティションを削除
STEP 2  需要側（流向＝INBOUND）
        2-1 料金用休日：自社の約款休日（料金適用フラグ＝1）を最優先、なければ土日祝
        2-2 従量手数料（買）を対象日で1行に畳む
        2-3 定額手数料の暫定単価 ＝ 前月の定額総額 ÷ 前月の総約定量（買）
        2-3b 基本料金の日割試算：実量制は実量kW判定ビューの当月値、それ以外は契約kW。
             1コマあたり ＝ kW ÷（グループ内地点数 × 月日数 × 48）
        2-4 需要実績に契約・メニュー・カレンダー・損失率・託送・容量拠出金・検針月・賦課金・税率・
             燃調・市場連動単価・非化石証書単価（環境価値付きメニューのみ）を結合（すべて対象日で期間解決）
             ・送電端換算電力量 ＝ 受電端 ÷ (1 − 損失率)
             ・固定単価の分岐：夜間／休日／夏季ピーク／夏季昼間／平日昼間（メニューの優先規則で切替）
             ・託送従量単価の分岐：03-2
        2-5 BG単位の市場調達原価：約定明細から約定代金と従量手数料を別列で合算
        2-6 BG単位のインバランス精算額：インバランス日次マートから
        2-7 先物差金のコマ割戻し：Base は全コマ、Peak は取引所営業日の 17〜40 のみ
        2-7b 相対・PPA の精算額：専属調達契約（需要家契約に紐付くもの）は専属先需要家（群）へ送電端需要比で直接配分、
             それ以外はエリア単位で合算して送電端需要比でセグメントへ按分（専属分は一括按分から除外し二重計上しない）
        2-8 セグメント集計（日×コマ×エリア×BG×INBOUND×セグメント×メニュー種別）
             費目ごとに Σ(電力量 × 単価)。賦課金は税込総額と税抜換算参考値の両方。
             非化石証書原価 ＝ Σ(受電端実績 × 証書単価)（環境価値種別「なし」のメニューは 0）
        2-9 BG単位・エリア単位の原価を「送電端需要比」でセグメントへ按分
             按分比 ＝ 当該セグメントの送電端需要量 ÷ 同一（日・コマ・エリア・BG）の送電端需要量合計
             相対・PPA のみエリア単位の送電端需要比
        INSERT：売上＝内訳の和、原価＝内訳の和（賦課金納付 cost_levy_passthrough ＝ rev_levy を含む）、
             コマ限界利益①＝従量電力量料金売上 − JEPX約定代金 − JEPX従量手数料 − 相対・PPA・先物、
             粗利②＝売上−原価（賦課金は両側相殺）、集計時ステータス＝確報値
STEP 3  発電側（流向＝OUTBOUND、セグメント＝発電、メニュー種別＝FIP／非FIP）
        3-0 試運転判定：発電受給地点マスタの 試運転開始日 ≤ 対象日 ＜ 商業運転開始日 を試運転期間とする
        売上 ＝ 発電量 × エリアプライス（マイナス価格は負のまま）
             ※ 試運転期間かつ「売電を計上しない」設定の地点は 0
             ＋ FIP：発電量 × 最大(0, F − A)（確定A値優先）＋ 発電量 × バランシングプレミアム
             ※ FIP交付金は商業運転開始日以降に限定（試運転期間は 0）
        原価 ＝ 発電量 × 売り従量手数料 ＋ 発電側課金（課金起算基準が系統連系日、または商業運転開始日以降のみ）
        コマ限界利益①＝市場売電 − 売り従量手数料、粗利②＝売上−原価 を流向＝OUTBOUND の行に更新
STEP 4  検算（#1 電力量突合、#2 金額突合、#3 単価網羅）→ データ品質日次に記録、検算フラグ更新

STEP 5  蓄電・揚水（初期導入ではペンディング。呼び出しをコメントアウト）
STEP 6  集約マート（需要予測精度日次、コマ別集約マート）
```

## 3. コンソーシアムBG按分プロシージャのロジック詳細仕様

### 3.1 業務上の意味・背景

代表者が一送へ支払うBG総額（BGネットインバランス量 × 単価）を、BG協定書の方式で構成員へ**コマ単位**で配分し、内部精算の根拠を作る。方式は BG 単位で1つ（単純比率／固定シェア／原因者負担／個別精算）。どの方式でも「Σ按分額 ＝ BG総額」が成立しなければ精算に回さない。

### 3.2 物理仕様

出力先：BG構成員別インバランスファクト（02-3.6）。入力：需要実績（確報）、需要計画（当日計画の最新版）、需要家・契約・BG構成員・BG・損失率マスタ、インバランス単価。

### 3.3 Fit & Gap

| 確認事項 | 標準実装 | 協定書で異なる場合 |
|---|---|---|
| 端数の負担者 | 免責でない構成員のうち インバランス絶対値が最大の者 | 代表者負担なら役割＝代表を優先 |
| 免責構成員 | 按分額 0、端数も寄せない | — |
| 責任上限・運営手数料 | コマではなく月次精算で適用 | — |
| ハイブリッド方式 | パラメータ化して個別実装（Q-3） | — |
| 計画の基準 | 当日計画（ID）の最新バージョン。受電端なら送電端換算 | GC 時点の凍結行を使う場合は提出日時で選択 |

### 3.4 アルゴリズム

```
STEP 1  地点 → 構成員：計画・実績を送電端に揃えて コマ×構成員 で合算
        構成員実績量 ＝ Σ 受電端実績 ÷ (1 − 損失率)
        構成員計画量 ＝ Σ 計画kW × 0.5（受電端基準なら ÷ (1 − 損失率)）
        地点と構成員は「契約の需要BG ＝ 構成員のBG」かつ「需要家の取引先ID ＝ 構成員の取引先ID」で紐付け
STEP 2  BG集計：BG全体インバランス量（ネット）、免責除く Σ|構成員インバランス|、原因者側 Σ|I|、有効構成員数
STEP 3  暫定按分額（協定書の方式で分岐）
        免責               → 0
        個別精算           → −I_i × 単価
        固定シェア         → BG総額 × 固定シェア
        原因者負担         → 原因者のみ BG総額 × |I_i| ÷ Σ(原因者)|I_j|、非原因者は 0
        単純比率           → BG総額 × |I_i| ÷ Σ|I_j|
        【安全弁】Σ|I_j| ＝ 0（全員が同時同量を達成）→ 均等按分（BG総額 ÷ 有効構成員数）。
                 0÷0 の実行時エラーでバッチを止めない。適用方式に「EQUAL_SPLIT」を記録して追跡可能にする
                 ※ BGネットが 0 でも構成員間で相殺が起きているコマは通常方式で按分する（緩和者・原因者の区別を残す）
STEP 4  べき等：対象日パーティションを削除
STEP 5  端数調整と挿入
        各構成員の暫定額（未丸めのまま按分額（未丸め）に保持）を、協定書の1円精算規定に従い1円単位に四捨五入
        コマ×BG ごとに 端数差分 ＝ BG総額 − Σ四捨五入額 をウィンドウ関数で算出
        負担者（免責でない かつ |I_i| 最大。協定書により代表者優先）の按分額に端数差分を加減算し、端数調整額に記録
        → Σ按分額 ＝ BG総額 が1円単位で厳密に成立
検算    コマごとに Σ按分額 と 四捨五入(BG総額) を突合。不一致があれば強制停止
```

**【業務上の意味・背景】**

**【アルゴリズム】**

```

1. パラメータ候補の抽出：メニュー×エリア×対象日で有効な行のうち、
     POINT   行（需要地点番号 一致）
     CUSTOMER 行（需要家ID 一致）
     MENU    行（顧客・地点 NULL）

3. 単価算出：市場連動単価 ＝ エリアプライス ÷ (1−損失率) ＋ 託送従量単価 ＋ 調達調整単価 ＋ 小売固定手数料 ＋ 業務管理費 ＋ 容量転嫁単価（すべて円/kWh）
4. クランプ：上限が登録されていれば 最小(単価, 上限)、下限が登録されていれば 最大(単価, 下限)
   （上限 ≥ 下限 をマスタ登録時に検証）
5. 例外：承認者が空の行は候補から除外。有効な行が 0 の日は単価 NULL → 日報バッチの前提チェックで停止
登録時検証：スコープと列の整合（CUSTOMER は需要家ID必須・地点 NULL、POINT は逆、MENU は両方 NULL）、
            同一スコープの期間重複禁止、上位スコープ（MENU 行）の同期間存在（特約が切れた日にフォールバック先を失わない）
```

## 5. 高圧実量制契約kW動的判定ロジック仕様

**【業務上の意味・背景】**
高圧の実量制では、契約電力（kW）を「当月を含む過去12ヶ月の最大需要電力」で決める。地点ごとに判定する約款と、1契約で複数地点を束ねて合算判定する約款（グループ実量制）が混在するため、契約履歴の契約グループIDの有無で判定単位を自動で切り替える。基本料金（小売・託送）の日割試算と月次確定の根拠。

**【物理仕様】** 実量kW判定ビュー（Gold）。出力：対象月、判定単位キー、電圧クラス、当月最大kW、判定契約kW、実績あり月数、契約開始からの暦月数、窓内欠損月数、暫定フラグ。

**【Fit & Gap】** 個別判定かグループ合算か（約款）。グループ基本料金の地点別内訳の按分基準（標準：当月の地点別最大kW比。約款に特異な定めがあれば調整列で吸収）。

**【アルゴリズム】**

```
判定単位キー ＝ 契約グループID があればそれ、なければ需要地点番号
STEP 1  コマ合算：同一（判定単位キー・対象日・コマ）の実績電力量を合算 → コマkW ＝ Σ kWh × 2
        （個別判定では地点1件、合算では複数地点の和。実績は実績時系列統合ビューから）
STEP 2  月次最大：月ごとの最大コマkW。月番号は「年×12＋月」の連続整数で持つ
        （YYYYMM の整数では年跨ぎ（202512 → 202601）で窓から外れるため）
STEP 2' 暦月骨格：判定単位ごとに「契約開始月〜当月」の暦月を1行ずつ生成し、月次最大を左外部結合
        実績のない月（新設・通信障害）も NULL の行として存在させる
STEP 3  12ヶ月ホールド：暦月で連続した12行の窓で 最大(月次最大kW) → 判定契約kW（NULL は無視）
        実績あり月数（新規契約の判定）、契約開始からの暦月数、窓内欠損月数（1以上ならアラート）を併記
        窓に未確定月・欠損月が1つでもあれば 暫定フラグ＝1（確定値受領後にリランで確定）
月次基本料金 ＝ 判定契約kW × 基本料金単価（小売）／× 託送基本料金単価（託送）
グループ合算時の地点別内訳 ＝ グループ基本料金 × 当月の地点別最大kW ÷ Σ地点別最大kW
日次の日割試算 ＝ 判定契約kW（暫定含む）÷（グループ内地点数 × 月日数 × 48）を各コマに計上し、月次確定で最大kW比に置換
```

## 6. 需要予測精度（MAPE／バイアス）自動監査ロジック仕様

**【業務上の意味・背景】**
経営陣と需給管理者に予測モデルのブレを毎日報告し、「モデルの実力」と「顧客の取引先休日の登録漏れ」を切り分ける。実績（受電端）は損失率で送電端に換算し、前日計画（送電端基準）と基準を揃えてから差分を取る。

**【物理仕様】** 需要予測精度日次マート：対象実需給日＋需要地点番号＋予測モデルバージョン（複合PK）、実績量（送電端）、計画量（送電端）、絶対誤差、MAPE（%）、WAPE（%）、バイアス(kWh)、バイアス率、評価コマ数、公的休日フラグ、顧客休日フラグ、想定稼働率、生成日時。パーティション：対象実需給日、クラスタ：需要地点番号。

**【Fit & Gap】** 閾値の初期値（高圧：地点 WAPE ＞ 10%、低圧：ポートフォリオ WAPE ＞ 5%、登録漏れ：バイアス率 ＜ −30% かつ 計画量 ≥ 1,000kWh）は運用開始後に実測で調整する。

**【アルゴリズム】**

```
STEP 1  前日計画（DA）の最新バージョンを地点×コマで1行に解決。送電端基準を優先し、受電端しかなければ損失率で換算
STEP 2  コマ単位：実績（送電端換算）、計画（送電端）、絶対誤差、符号付き誤差（実績−計画）
        休日属性：公的休日フラグ（日付カレンダー）、顧客休日フラグ・想定稼働率（取引先休日マスタ。地点限定行を優先）
STEP 3  地点×モデル で日次集約
        MAPE ＝ 平均(|誤差| ÷ 実績) × 100   … 実績 0 のコマは安全除算で NULL とし平均から除外（参考指標）
        WAPE ＝ Σ|誤差| ÷ Σ実績 × 100        … 実績 0 コマの影響を受けない（閾値判定の主指標）
        バイアス ＝ Σ(実績−計画)（プラス＝過小予測、マイナス＝過大予測）、バイアス率 ＝ バイアス ÷ Σ計画
STEP 4  登録漏れ検知：公的休日＝0 かつ 顧客休日＝0（稼働日として予測）なのに バイアス率 ＜ −30% の地点を抽出
        → 予測アルゴリズムを疑う前に、営業・CS へ取引先休日マスタの更新漏れを確認（Q-13 のエスカレーション）
        顧客休日＝1 で想定稼働率が登録されているのに外している場合は、モデルが特徴量を取り込めていない側の問題
```

## 7. 先頭3桁地点特定番号検証関数の仕様

**【業務上の意味・背景】** 供給地点特定番号（22桁）にはチェックデジットがなく数式で自己検証できないため、番号の構造（先頭2桁＝エリア、3桁目＝電圧区分）を使った先頭3桁の有効性チェックで代替する。API・画面・ETL・移行のすべての入口で同一関数を適用し、不一致は登録・投入を拒否する。3桁目の不一致は「番号の打ち間違い」だけでなく「電圧クラスの登録誤り」を検出する。

**【物理仕様】** ユーザー定義関数（入力：地点番号、エリアコード、電圧クラス／出力：判定コード文字列）。BigQuery は CHECK 制約を持たないため、テーブル定義では強制せず、ステージング層・移行スクリプト・マスタ更新手続きのゲートとして呼び出す。

**【アルゴリズム（評価順）】**

| 順 | チェック | 判定コード |
|---|---|---|
| 1 | 22桁の半角数字であること | 桁数・形式エラー |
| 2 | 先頭2桁が 01〜09 であること（10＝沖縄はスコープ外） | スコープ外エラー |
| 3 | 先頭2桁 ＝ 登録エリアコード | エリア不一致エラー |
| 4 | 電圧クラス 低圧 → 3桁目 ＝ 0、高圧・特高 → 3桁目 ＝ 1 | 電圧区分エラー |
| 5 | 電圧クラスが 低圧／高圧／特高 のいずれか | 電圧クラス不明エラー |
| — | すべて通過 | OK |

スコープ判定をエリア一致より先に評価し、沖縄番号が「エリア不一致」ではなく「スコープ外」として報告されるようにする。移行スクリプトは OK 以外が1件でもあれば最初の不正コードと件数を付けて強制停止する。

**【Fit & Gap】** 発電受給地点も同一規則。約款上の「特別高圧」表記は取込時に「特高」へ名寄せする。

## 1. BI抽出同期・完了監視プロシージャのロジック詳細仕様

### 1.1 業務上の意味・背景

日報ダッシュボード（P1／P2）は Looker Studio の**抽出（Extract）データソース**で構築し、画面表示で BigQuery を叩かない（スキャン課金ゼロ・サブ秒描画）。副作用は「抽出した瞬間の数字で固定される」ことなので、**日報バッチ完了 → 検算 → 抽出更新 → 完了確認 → 公開通知**の順序を崩さないことが速さより優先される。検算NGの日は抽出に含めず、前日までの検算済みデータを表示し続ける（0行で更新して画面を白紙にしない）。誤った数字を「最速で」配るのが最悪の結果である。

抽出データソースとライブ接続（P3：コマ粒度）は**別レポートファイル・別URL**に分離する。同一ファイル内でデータソースをまたぐクロスフィルタを行うと、ブレンドが発生するかフィルタ引継ぎに失敗し、描画停止・エラー画面に陥る。

### 1.2 物理仕様

| 項目 | 内容 |
|---|---|
| 抽出用ビュー | 日報損益マートを 日×エリア×BG×流向×セグメント×メニュー種別 に畳み、検算通過（検算フラグ＝1）の行だけを直近13ヶ月分に絞る。抽出生成日時列を持つ |
| 抽出更新 | Looker Studio のスケジュール更新（07:30 固定。バッチ SLA 07:20 ＋ 余裕10分）。公開 API で抽出更新をキックできる場合は完了イベントから直接呼ぶ（R-26） |
| 完了監視 | BI 抽出完了監視プロシージャ（バッチ実行ログ、日報損益マート、BigQuery ジョブ履歴を参照） |
| 公開フラグ | データ品質日次の（対象日・全エリア・SYSTEM）行の公開可否フラグ |

### 1.3 Fit & Gap

| 確認事項 | 影響 |
|---|---|
| Looker Studio の抽出更新 API の提供有無 | 提供されていればイベント駆動、なければスケジュール更新＋完了監視 |
| Looker Studio が BigQuery ジョブに付与するラベル（要求元＝Looker Studio、データソースID） | stg 環境で抽出更新を1回実行し、ジョブ履歴のラベルに想定のキーが入ることを確認 |
| Slack／PagerDuty の通知先と文面 | 公開通知（成功）と同期遅延警告（失敗）の2種 |

### 1.4 アルゴリズム

```
[07:00] 日報損益バッチ（B-05）開始（SLA：07:20 完了）→ バッチ実行ログに完了時刻を記録
[07:20] 検算（#1〜#3）→ データ品質日次に記録、日報損益マートの検算フラグ更新
[07:30] Looker Studio 抽出データソースのスケジュール更新（自動）
[07:35] 完了監視：5分間隔・最大6回（30分）。オーケストレータ（Cloud Composer）が1回判定の
        プロシージャを繰り返し呼ぶ（BigQuery スクリプト内でループ待機しない）

  1) 品質ゲート：対象日（昨日）の日報損益マートの検算フラグが 全行 1（最小値で判定。最大値では一部NGを見逃す）
     かつ バッチ実行ログに B-05 成功の完了時刻がある
     → NG なら 公開可否＝0 に更新、状態「検算未通過で遮断」を返して終了（リトライしない。アラート）
  2) 抽出完了検知：BigQuery ジョブ履歴から次をすべて満たすジョブを数える
     (a) 要求元ラベル ＝ Looker Studio、データソースIDラベル ＝ P1/P2 抽出データソース
     (b) ジョブ作成時刻 ≥ B-05 完了時刻（バッチ遅延時に前日データを吸った抽出を「完了」と誤判定しない）
     (c) 状態 ＝ 完了 かつ エラーなし
     (d) 参照テーブルに抽出用ビューを含む
  3) 1件以上 → 公開可否＝1 に更新、状態「公開」を返す → Slack「本日の日報を公開」
     0件     → 状態「抽出未検知」を返す → 5分後に再実行。6回目でも未検知なら同期遅延警告・公開通知は出さない
              （画面は前日抽出＋「更新待ち」表示。バッチ完了後の手動更新を運用手順に含める）
```

## 2. 10年保持と自動長期保存料金適用方針

**【業務上の意味】** 監査・精算の原本（月次確定）から経営マート（日報損益・月次経営サマリ・BG月次精算）まで、**すべて本番の BigQuery 上に10年保持**する。別ストレージへの退避・復元手順を持たないことで、過去の再計算（バックフィル、締め済み期間の承認付きリラン）を同じ SQL で実行できる。

| 層 | 対象 | 保持 | 期限後 |
|---|---|---|---|
| 生データ | 全て | 10年 | 長期保存料金が自動適用 |
| 事実ファクト | 速報ストリーム／速報最新行キャッシュ | 7日／7日 | パーティション有効期限で自動削除 |
| 事実ファクト | 日次確報 | 13ヶ月 | 同上（確定が原本） |
| 事実ファクト | 月次確定・マスタ・監査ログ | 10年／無期限 | 本番上。コールドへ移さない |
| 集計マート | コマ別集約（Active） | 直近2年（有効期限 737日） | 境界日パーティションを日次で Cold へメタデータコピー（DML DELETE は使わない） |
| 集計マート | コマ別集約（Cold） | 2年超〜10年 | 更新が入らないため長期保存料金が自動適用 |
| 集計マート | 日報損益・月次経営サマリ・BG月次精算 | 10年 | 本番上 |

**【コスト設計】** BigQuery は90日間更新のないパーティションのストレージ料金を自動的に長期保存料金（アクティブの約半額）へ切り替える。確定層とマートは書込後に更新されないため、10年分の大半が自動的に長期保存料金となり、退避運用なしで保持コストが極小化する。保持期限はパーティション有効期限で機械的に管理し、**手動削除・DML による大量削除を行わない**（スロット消費と同時実行コンフリクトの回避）。

**【Fit & Gap】** 法定保存期間（帳簿書類）と社内規程の保持年限。Cold の分割目的はコストではなく「BI が古いパーティションを絶対に読まないこと」と「Active を小さく保つこと」である点の理解。

### 3.2 祝日CSV取込のフェイルセーフ（検疫・アラート制御）

**【業務上の意味・背景】** デジタル庁の祝日CSVは唯一のソースだが、ヘッダー名・日付区切り・文字コード・列順が予告なく変わりうる。パース失敗で取込バッチを異常終了させると、次に走るカレンダー生成が失敗または空更新となり、**未来日の料金休日判定・需要予測特徴量がすべて「平日」で上書きされる二次災害**に繋がる。

**【アルゴリズム】**

```
1. 取得   配信URL（設定値）から取得し、生データ層に 1行1レコード で無加工保持（ファイルハッシュ記録。前回と同一ならスキップ）
2. 変換   Shift_JIS → UTF-8（変換失敗も受入不可）。日付は 年/月/日 → 年-月-日 → 年月日 の順で安全パース
          ヘッダーは固定文字列一致ではなく「最初にパースできない行」として扱う（ヘッダー名変更に耐える）
          パース失敗行は検疫テーブルへ（バッチは落とさない）
3. 区分   名称の部分一致で 振替休日／国民の休日／国民の祝日 を判定。判定不能は「臨時」で取込みアラート
3b. 受入判定（すべて満たす場合のみ更新）
          (a) パース成功行数 ≥ 前回成功時の行数 × 0.9
          (b) 検疫行数 ≤ 3
          (c) 今年と翌年の 1月1日 が含まれる（少なくとも直近2年分が読めている）
          (d) 同一日付の重複がない
          NG → 汎用休日マスタを一切更新せず前回成功時を維持、状態「受入不可」を返し 緊急アラート（PagerDuty／Slack）
               カレンダー生成（B-11）は起動しない（既存の導出列が保たれる）
4. 更新   休日日付をキーに MERGE。CSV から消えた日付は削除せず「取消」に更新して履歴を残す
5. 差分   追加・削除・名称変更を前回と比較して通知
6. 波及   差分があれば B-11 を起動し、影響日のみ導出列を更新
```

閾値（0.9／3）は設定値として外出しする。祝日の年間件数に対して行数比 0.9 は厳しめであり、掲載年数が減った場合に誤検知しうるため初回運用で実測して調整する。

| リスク | 影響 | 対策 |

| 契約履歴の期間に重複・隙間が多い | フェーズ2が長期化し、日報の単価が引けない | 抽出時点で検証 SQL による重複・隙間レポートを出し、業務側の是正を並行で進める |

| 22桁番号にチェックデジットがない | 誤登録が実績取込失敗として後から発覚 | 先頭3桁検証を全入口で強制し、加えて初回取込時に**一送の検針データ（速報・確報）に当該地点番号が存在すること**を突合して存在確認する（番号構造が正しくても実在しない番号を排除） |
| BG協定書の按分方式が文書化されていない | 按分方式が決まらずフェーズ3の突合ができない | 代表者の過去通知額から方式を逆算し、規約担当者と確認 |
| 祝日CSVのフォーマットが予告なく変わる | 取込停止とカレンダーの「平日」上書き | 受入条件を満たさなければマスタを維持し緊急アラート。カレンダー生成は受入成功時のみ起動 |
| 高圧・特高の託送メニューが一律と時間帯別で混在 | 単価解決 SQL が電圧クラスごとに分岐し保守不能 | 託送料金マスタを時間帯別列付きの1テーブルに統一し、空値は標準単価へフォールバック |
| 過去データの生データ原本が残っていない | 再処理ができない | 移行時点からは全て生データ層に残す。過去分は「再処理不可」と明記して割り切る |
| 並行稼働で既存日報と一致しない | 商用開始の判断ができない | 差異を「本基盤が正しい」「既存が正しい」「定義差」に分類し、定義差は設計仕様書に追記 |
