## 1. 目的と範囲

- ヒアリングシート兼適合分析表で決まった内容を反映した設計・ソースコードを、導入先の環境へ配備し、既存のマスタと過去データを移行して、商用運用を開始する。
- 蓄電・揚水（オプション）は初期導入の範囲に含めない（[詳細設計書 第4部 4. 蓄電・揚水オプションの分離](../05_詳細設計/詳細設計書.md#4-蓄電揚水オプションの分離)）。導入先がヒアリング F21-01 で初期導入に含めると決めた場合は、本書のフェーズ3・4に追加する。

## 3. データインポートの原則と依存関係

### 3.1 依存レベルの概要

```
レベル1  独立マスタ          エリア、事業者、電源種別、30分コマカレンダー、休日判定ルール、消費税率、JEPX取引手数料
   │
レベル2  従属基礎マスタ      送電損失率、託送料金（一律／季節別時間帯別）、容量拠出金、再エネ賦課金、非化石証書価値、
   │                          燃料費調整、FIPバランシングコスト、精算丸めルール、汎用休日（祝日CSV）、会計年度
   │
レベル3  契約・カレンダー    日付カレンダー（生成）、取引先休日、需要家（PII分離）、需要家契約履歴、発電所・受給地点、
   │                          料金メニュー、市場連動独自パラメータ、BG・BG構成員、検針サイクル、相対・PPA契約
   │
レベル4  ファクト            市場価格（スポット／時間前）・約定明細・インバランス単価・A値・先物・相対PPA精算・非化石証書購入、計画、実績（速報／確報／確定）、受領状況、
   │                          BG構成員別インバランス、監査ログ、バッチ実行ログ
   │
レベル5  Gold                日報損益、インバランス日次、コマ別集約（Active／Cold）、月次経営サマリ、品質日次、
                              予測精度日次、BG月次精算、休日スナップショット、実量kW判定ビュー、抽出用ビュー、BI公開
```

**原則**：上位レベルの完了条件（バリデーション全件パス）を満たさない限り下位へ進まない。すべてのマスタは期間管理で投入し、暫定値は備考に「暫定」を記録して確定後に期間で差し替える。

### 3.2 インポートの原則

- **必ずレベル1から順に投入する。** 外部キー制約と論理的整合性（期間管理の `BETWEEN` 参照）を破綻させないため。
- 同一レベル内でも依存がある場合は、表に示した順序を守る。
- 各レベルの投入後に 13.1 のバリデーション（期間重複・隙間・参照整合・22桁整合）を実行し、**全件パスしてから次のレベルへ進む**。
- マスタの初期投入も `fact_master_change_log`（FT-10）に記録する（初期値の出所を後から辿れるようにする）。

## 5. 移行時のリスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 契約履歴の期間に重複・隙間が多い | F2 が長期化し、日報の単価が引けない | 既存システムからの抽出時点で重複・隙間レポートを出し、業務側の是正を並行で進める |
| 約款の一次情報（ヒアリング F03-01・F03-02）の入手が遅れる | F1 の初期マスタが確定せず F3 の検算が回らない | 暫定値で投入して `remarks` に「暫定」を記録し、確定後に期間管理で差し替える |
| 22桁番号にチェックデジットがなく、打ち間違いを数式で検出できない | 誤登録が実績の取込失敗（地点未存在）として後から発覚する | 先頭3桁チェック（13.1 ③）を全入口で強制し、加えて初回取込時に一送の検針データ（速報・確報）と地点番号を突合して存在確認する（番号構造が正しくても実在しない番号を排除する） |
| BG規約の按分方式が文書化されていない | `allocation_method` が決まらず F3 の突合ができない | 代表者の過去の通知額から方式を逆算し、規約担当者と確認する |
| 過去データの Bronze 原本が残っていない | 再処理ができない | 移行時点からは全て Bronze に残す。過去分は「再処理不可」と明記して割り切る |
| 並行稼働で既存日報と一致しない | 商用開始の判断ができない | 差異を「本基盤が正しい（既存の誤り）」「既存が正しい（本基盤の誤り）」「定義差」に分類し、定義差は基本設計書に反映する |
| デジタル庁祝日CSVのフォーマットが予告なく変わる | B-10 が停止し、B-11 が未来日を「平日」で上書きする二次災害 | 12.7 のフェイルセーフ（受入条件を満たさなければマスタを維持し緊急アラート）。B-11 は受入成功時のみ起動 |
| 高圧・特高の託送メニューが一律と季節別時間帯別で混在 | 単価解決の SQL が電圧クラスごとに分岐し保守不能になる | D-11 を時間帯別列付きの1テーブルに統一し、`COALESCE` で一律メニューへフォールバック（11.5） |

## 7. 配備手順

配備の単位は [ソースコード説明](../06_ソースコード/ソースコード説明.md) に示すファイル群、配備用の結合版は同じフォルダの `ALL_IN_ONE.sql`（デプロイ順：テーブル定義 → 関数 → ビュー → プロシージャ）とする。

1. テンプレート変数（`${GCP_PROJECT_ID}`、`${BQ_DATASET_*}`）を CI/CD で環境別の値へ展開する。未展開のまま実行してはならない。
2. CI で未展開の変数（`${GCP_PROJECT_ID}`、`${BQ_DATASET`、`TODO`、`CHANGE_ME`）を検出した場合は配備を拒否する。
3. 展開後の SQL を dev で dry run し、処理バイト数のベースラインを取得する。
4. テスト用データセットへ適用し、プロシージャの単体実行と検算を確認する。
5. dev → stg → prod の順に適用する。Silver 以降の変更は、stg で Bronze からの再構築テストを通してから prod へ適用する。
6. オーケストレータ（Workflows／Cloud Composer）から、実行ID（`p_run_id`）と処理コードの版（`p_pipeline_version`）をプロシージャへ渡す。版の採番方式はヒアリング N04-01 の決定に従う。

## 8. 受入基準

- フェーズ1〜4の完了条件（本書 4.2）をすべて満たすこと。
- 検算 #2（金額突合）が対象全月で1円単位に一致し、検算 #3（単価網羅）が 0 件であること。
- 並行稼働期間中の日次粗利差異が閾値内であり、既存日報との差異が説明可能な項目のみであること。
- ヒアリングシートの制度確認の項目がすべて記入され、差異時の対策が基本設計書に反映されていること。未確認の項目が残る場合、当該項目に依存する検算（金額突合）はフェーズ3の完了条件から一時除外し、確認後に再実行する。
- 監視アラートが想定どおり発報し、運用手順書（障害時の再処理手順を含む）がレビュー済みであること。
