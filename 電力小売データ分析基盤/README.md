## 2. 参照のルール

- **一方通行**：各文書は、自分より上流の工程の文書だけを参照する。上流の文書は下流の文書を参照しない。下流の文書は各章・各節の冒頭に「入力」または「対応機能」「関連知識」として根拠を示すため、どの設計・実装がどの要件と知識から来ているかを、下流から上流へたどれる。
- **機能ID**（F-01〜F-21、N-01〜N-06）は機能一覧で定義し、ヒアリングシート・基本設計書で共通に使う。
- **ヒアリング項目ID**（例：F03-01）はヒアリングシートで定義する。基本設計書などで「ヒアリング F03-01」とあれば、その項目の確認結果に従うことを示す。
- **GAP の影響範囲の特定**：ヒアリングシートで GAP と判定した項目は、機能ID から基本設計書の「本書の入力と対応機能」の表で影響する章を、さらに詳細設計書の各節の「入力」から影響する節を特定する。ソースコードは [ソースコード説明](06_ソースコード/ソースコード説明.md) の「根拠となる設計」から特定する。
- **変更の順序**：要件や制度が変わった場合は、ヒアリングシート → 基本設計書 → 詳細設計書 → ソースコード → 導入・運用の順に改訂する。下流だけを直して上流と食い違わせない。
- 外部の規約として [データ基盤開発運用ガイドライン](https://github.com/dpftriv/bigquery-dev-2nd-operation-guideline)（設計書中の「命名・運用定義書」「規約」）に準拠する。

## 4. 基本知識の読み方

電力小売のデータ基盤は、一般的なデータウェアハウスの知識だけでは作れない。30分コマ、送電端と受電端、速報・確報・確定、検針月基準の単価、按分、公的資金のパススルーといった業界固有の前提を知らないまま設計すると、動くものはできても「1円が合わない」「深夜に前日が消える」「粗利が賦課金分だけ過大」といった形で、後から必ず跳ね返ってくる。基本知識は、その前提を「知識体系 → 初級 → 中級 → 上級 → 応用」の順で身につけ、設計書と SQL を自分の言葉で読めるようになるための教材である。

| # | 資料 | 到達目標 | 想定読者 | 目安 |
|---|---|---|---|---|
| ① | [知識体系](01_基本知識/01_知識体系.md) | 業務・制度・データ・会計・指標を「同じ定義でつなぐ」全体の地図を持つ | 全員 | 2時間 |
| ② | [講義 初級 業界基礎知識](01_基本知識/02_講義_初級_業界基礎知識.md) | 業界の言葉と仕組みを、システム用語なしで自分の言葉で説明できる | 初めて電力データに触れる全員 | 3時間 |
| ③ | [講義 中級 数字ができるまでを一日追う](01_基本知識/03_講義_中級_数字ができるまでを一日追う.md) | 1需要家×1コマの粗利を、費目別に手で組み立てられる | 分析・開発の担当者 | 4時間（手計算を含む） |
| ④ | [講義 上級 設計判断と事業経済性](01_基本知識/04_講義_上級_設計判断と事業経済性.md) | トレードオフの中で判断し、根拠を数字で示せる | リード・アーキテクト・事業側の意思決定者 | 3時間 |
| ⑤ | [講義 応用 実務の落とし穴](01_基本知識/05_講義_応用_実務の落とし穴.md) | 実務の罠を「どの流れが壊れるか」として説明し、設計レビューで指摘できる | 設計・レビュー・運用の担当者 | 3時間 |

**この順序にしている理由**

- ①を最初に置くのは、後の講義で出てくる「時間の分離」「確定性」「粒度」「版管理」という言葉の意味を、先に地図として持ってもらうため。ここを飛ばすと、②以降の各論が個別の暗記になる。
- ②→③で、業務の仕組みが「数字」になる過程を追う。③の手計算を実際にやることを強く勧める。電卓で1コマの粗利を出した人と、読んだだけの人では、設計書の読み方が変わる。
- ④を⑤より先に置くのは、**判断軸を持ってから罠を見る**ため。⑤の17の罠は、④で示した「再現性は容量より重い」「失敗は変えないで守る」「同じ費用を2回乗せない」といった判断軸の具体例として読めるようになっている。
- ⑤は最後に読む資料であると同時に、**構築中・運用中に何度も戻ってくる資料**である。設計レビューの前、リリース前、月次の請求突合でズレが出た時に、該当する章を引く使い方を想定している。

基本知識の数値例（単価・損失率・件数）はすべて説明用であり、実際の値は約款・公表値・契約に従う。
