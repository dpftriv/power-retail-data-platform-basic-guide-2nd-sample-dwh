## 2. 処理コードの版（`pipeline_version`）の扱い

規約で `pipeline_version` に触れているのは次の3箇所で、値の採番方式は指定していない。規約が求めるのは、(a) 列として持つこと、(b) 意味は処理コードの版であること、(c) べき等性の判定材料として実行ID・入力範囲・対象テーブルとセットで永続化すること、の3点である。

| 箇所 | 記載 |
|---|---|
| 18.1 監査メタデータ | `pipeline_version`：処理コードまたはモデルの版 |
| 11.2〜11.4 DDL標準 | 全テーブル例に `pipeline_version` 列を含む（列の存在が標準） |
| 21.2 二重発行防止 | 再試行時は、実行ID、入力範囲、対象テーブル、コードバージョンを永続化する。ジョブIDだけを冪等性キーとみなしてはならない |

本基盤では次のように扱う。

1. **値の生成元は CI/CD**：配備処理が確定させる値であり、SQL 本文にリテラルで書かない。
2. **オーケストレータが実行時に渡す**：Workflows／Composer が「配備時に記録されたコード版」と「実行ID」を組にしてプロシージャへ渡す。
3. **べき等性との接続**：実行ID ＋ 入力範囲（対象実需給日または請求月）＋ 対象テーブル ＋ 処理コードの版の4点をバッチ実行ログに記録し、再実行時は同じ実行ID の成功済み判定に使う。
4. **採番方式**：Git コミットSHA、リリースタグ、dbt／Dataform のリリース識別子のいずれでもよい。桁数・形式を組織で統一し、データ辞書へ登録する。採番方式は [ヒアリングシート 環境分離・配備](../03_要件定義/ヒアリングシート兼適合分析表.md#n-04-環境分離配備) の項目 N04-01 で決める。

## 3. 確認の範囲

- 静的な文字列・構文の確認であり、BigQuery 上での構文検証（dry run）は配備時に行う。真偽値型と監査列は全プロシージャに及ぶため、配備前に dev 環境での dry run と単体テストを必須とする。
- 規約 8（個人情報）と規約 16 以降（権限、CI/CD、災害対策・事業継続、人工知能の利用管理）は SQL 単体では判定できないため、確認の対象外とする。個人情報の列は `pii_` 接頭辞で分離済みで、Policy Tags の付与・IAM・行レベルのアクセス制御は基盤構築時に設定する。
- 規約 10.1／10.4 はパーティション・クラスタリングの採否を実測に基づいて決めることを求めている。本書は設定の有無を確認したものであり、効果の検証は配備後に行う。
