# 電力小売 データ分析基盤 導入ガイド — README

**更新日**：2026-09-10
**対象**：電力小売会社で初めてデータ分析基盤の導入・構築・運用に関わる方（事業側・IT側の双方）
**書き手の立場**：電力小売の現場で10年以上、需給・料金・精算の業務と、データ分析基盤の構築・運用を続けてきた者として、「最初に知っていれば避けられた失敗」を、次に取り組む方が繰り返さないように残しておく。

---

## 1. この資料一式の目的

電力小売のデータ基盤は、一般的なDWHの知識だけでは作れない。30分コマ、送電端と受電端、速報・確報・確定、検針月基準の単価、按分、公的資金のパススルー——業界固有の前提を知らないまま設計すると、動くものはできても「1円が合わない」「深夜に前日が消える」「粗利が賦課金分だけ過大」といった形で、半年後に必ず跳ね返ってくる。

この一式は、その前提を「知識体系 → 入門 → 中級 → 上級 → 応用」の順で身につけ、設計仕様書と SQL を自分の言葉で読めるようになるための教材である。仕様書そのもの（別バンドル `repo_en/spec.md`）と SQL リポジトリは別途配布しており、本ガイドはその「読み方と、なぜそう設計されているか」を教える位置づけになる。

**この順序にしている理由**

- ①を最初に置くのは、後の講義で出てくる「時間の分離」「確定性」「粒度」「版管理」という言葉の意味を、先に地図として持ってもらうため。ここを飛ばすと、②以降の各論が個別の暗記になる。
- ②→③で、業務の仕組みが「数字」になる過程を追う。③の手計算を実際にやることを強く勧める。電卓で1コマの粗利を出した人と、読んだだけの人では、仕様書の読み方が変わる。
- ④を⑤より先に置くのは、**判断軸を持ってから罠を見る**ため。⑤の17の罠は、④で示した「再現性は容量より重い」「失敗は変えないで守る」「同じ費用を2回乗せない」といった判断軸の具体例として読めるようになっている。
- ⑤は最後に読む資料であると同時に、**構築中・運用中に何度も戻ってくる資料**である。設計レビューの前、リリース前、月次の請求突合でズレが出た時に、該当する章を引く使い方を想定している。

## 3. 各資料の要点（何が書いてあるか）

### ① 知識体系
業務・制度・データ・会計・KPI・分析軸・ガバナンスを一つの体系として整理した共通土台。「六つの時間（対象・受渡・取得・更新・確定・計上）」「データ状態と改訂番号」「単価を独立した知識として管理する」「税区分を混在させない」「SCD Type 2 が必要なマスタ」など、後の講義と設計仕様書がすべて前提にする原則が置かれている。実装の細部ではなく、**定義を揃えるための地図**として読む。

### ② 初級・入門編
電気事業の三層構造、9エリア、30分コマ、計画値同時同量、送電損失率、二階建て料金、実量制、JEPX、PPA・VPPA、専属調達、先物、FIT/FIP、賦課金、容量拠出金、発電側課金、分散検針、会社休日。19項目を「やさしい解説／仕組みと背景／前提常識／数字のイメージ」で説明する。システム用語は一切使わない。

### ③ 中級
2026年9月9日・東京エリア・高圧1地点を題材に、計画→速報→確報→確定の流れ、1コマの売上と原価の費目別積み上げ、BG按分・エリア按分・日割の3種類、期間管理、粒度と集計軸、3つのカレンダー、3つの検算を、実際の金額で通しで追う。夏の昼ピークが赤字になる典型と、月末に試算が確定に置き換わる仕組みまで。

### ④ 上級
3層に分ける本当の理由、べき等性、締め済み期間の承認制、安定識別子、検算→抽出→公開の直列化、「止まる」ではなく「変えない」で守る失敗設計、監査に耐える記録、事故の前兆から逆算する監視、ヘッジ比率と粗利の振れ幅、BG参加の損得、予測精度1%の価値、FIPアグリゲーション、蓄電のサイクル損益、スキャン量の設計、10年保持、移行順序、並行運用、制度変更への備え。各項目を「課題／設計判断と根拠／トレードオフ／判断基準の数字」で書いている。

### ⑤ 応用編
必ず踏む17の罠。合成単価、丸める層、送電端と受電端、深夜の空白、暫定と確定、訂正の追記、祝日CSVの二次災害、実量制の欠損月、アンペア契約、単価改定の3層、特約の行増殖、需要と発電の主キー衝突、VPPAの二重計上、専属契約の二重配分、先物の営業日、BG按分の0÷0、賦課金の粗利率歪み、検針月基準、発電側課金の見落とし、暫定A値、訪問検針、識別子の乱立、親会社の前提、試運転中の実績、届いた日と対象日。各罠を「何が起きるか／なぜ起きるか／正しい考え方／数字で見る影響」で書いている。

## 4. 導入を成功に導くために、最初に決めておくこと

私が過去の案件で「これを最初に決めていれば」と思ったことを、順に挙げる。資料を読む前でも、これだけは事業側と合意しておいてほしい。

1. **粒度と軸を先に決める**。日×30分コマ×エリア×BG×流向（需要／発電／蓄電）×セグメント×メニュー種別。後から軸を足すのは、全マートの作り直しになる。
2. **「どこで1回だけ丸めるか」を層で決める**。生データと事実データでは丸めない。丸めは請求元の約款に従い、月次で1回。この原則を破ると、請求突合は永久に合わない。
3. **単価が「いつ決まるか」を費目ごとに表にする**。基本料金は月末、賦課金は検針月、A値は翌月、インバランスは事後。日報は暫定、月次で確定。この表がないと、経営会議で「先月の数字が変わった」と言われ続ける。
4. **カレンダーを3つに分ける**。料金用（自社約款＋土日祝）、予測用（＋顧客休業日）、取引所営業日。混ぜた瞬間に、料金か予測か先物のどれかが壊れる。
5. **公的なお金の流れを区別する**。賦課金は預かって流すだけ（売上・原価の両側に同額）、FIPプレミアムとバランシングコストは交付金（不課税）、差金決済も不課税。課税・不課税を混ぜると消費税申告を誤る。
6. **確定値は上書きしない**。訂正は差分の追記。単価の更正は上書き＋影響日の再計算。この2方式の使い分けを運用手順に書く。
7. **失敗時は「変えない」**。外部データ（祝日CSV、約款）の取込は受入条件を満たした時だけ更新し、満たさなければ前回の状態を維持して緊急アラート。「止まる」設計は二次災害を起こす。
8. **検算→抽出→公開を直列化する**。検算を通った日だけBIに出す。速さより「間違った数字を出さない」を優先する。
9. **顧客休日の登録責任者を決める**。予測精度の悪化の大半は、モデルではなく休業日の登録漏れ。営業・CSの関与なしにシステムだけで解決しない。
10. **未決事項・要検証事項を番号付きで管理する**。約款・協定書・公表値の確認待ちを「設計イメージ」と明記し、確定したものと区別する。「完全網羅」「破綻なし」と断定する文書は、根拠が添えられていない限り信用しない。

## 5. 設計仕様書・SQL との対応

本ガイドは教材であり、実装の正本は次の2つ。

| 正本 | 内容 |
|---|---|
| `repo_en/spec.md` | 設計仕様書。第1章（基本前提）、第10章（計算ロジック）、第11章（日報バッチ）、第13章（検証）、第17章（未決・要検証事項）が本ガイドと最も対応する |
| `repo_en/sql/`（DDL・ビュー・プロシージャ） | 設計仕様書の参照実装。オブジェクト名は BigQuery データ基盤命名・運用定義書 5.2 に準拠（`dim_`／`fact_`／`agg_`／`snap_`／`v_`）。デプロイ前に dev 環境でレビューする前提 |
| `repo_en/docs/sql_standard_compliance_report.md` | 命名・運用定義書への適合チェック結果と残作業 |

## 6. 更新と保守

- 本ガイドの数値例（単価・損失率・件数）はすべて説明用であり、実際の値は約款・公表値・契約に従う。
- 制度改定（容量拠出金の方式、発電側課金の割引、賦課金単価、FIPの経過措置）があった場合は、②④⑤の該当項目と設計仕様書第17章を同時に更新する。
- 新たな失敗事例が出た場合は、⑤に追加する。⑤は「完成した資料」ではなく、現場の経験を積み上げる台帳として運用してほしい。

---

最後に。この一式を読み終えた方が、設計仕様書を開いて「なぜここはこう書いてあるのか」を自分で説明でき、レビューで「この設計はどの罠を避けるためのものか」を指摘できるようになっていれば、この資料の役目は果たせている。分からないことがあれば、④と⑤の該当章に戻り、それでも答えがなければ設計仕様書第17章の未決事項に追加してほしい。
