# 電力小売りデータ基盤 個別デザインガイド

**版**：1.1

**上位文書**：[データ基盤汎用デザインガイド](データ基盤汎用デザインガイド.md) v1.1

**対象**：北海道から九州までの9エリアを対象とする電力小売、発電、再エネアグリゲーションの商用データ基盤

**正規業務資料**：設計仕様書、詳細設計書

**適用関係**：本書は汎用デザインガイドのドメイン別適用文書である。本書に記載のない事項は汎用ガイドに従う。本書が汎用ガイドと異なる場合、電力制度・約款・業務要件に起因する差異だけを認め、差異と代替統制を本書へ記録する。

## 0. 実装環境標準

本書の実装・検証環境は、上位の[データ基盤汎用デザインガイド](データ基盤汎用デザインガイド.md)および[ローカル開発環境標準](ローカル開発環境標準.md)に従う。電力小売り固有のSQL、DQ、Terraform、CI/CD検証も、標準ツールのバージョンを前提とする。

## 1. 目的と適用範囲

本基盤は、需給、調達原価、インバランス、粗利、料金精算、容量拠出金、FIP、再エネ賦課金を、監査可能かつ再計算可能な形で管理する。業務上の最小粒度は30分コマであり、日報、月次精算、請求突合、BI公開を同一のデータ履歴から再現できることを目的とする。

対象は発電所・受給地点、需要家・契約、料金メニュー、市場取引、託送、需給管理、BG精算、FIP、制度費用、休日・カレンダー、日報分析である。蓄電・揚水は初期導入ではオプションとして分離する。

## 2. 汎用ガイドとの適用関係

| 項目 | 電力小売りでの適用 |
|---|---|
| データレイヤー | Bronze、Silver、Gold、Serving、Quarantine、Auditを基本とする |
| 命名 | `dim_`、`fact_`、`agg_`、`v_`、`snap_`を使用する |
| 時刻 | BigQueryの`TIMESTAMP`はUTC、業務キーはJSTの`target_date`と`slot_number`で管理する |
| パーティション | 大量ファクト・マートはアクセスパターンを検証したうえで`target_date`を標準候補とする |
| フィルター | ファクト・マートは原則`require_partition_filter = TRUE`とする |
| 金額 | `NUMERIC`または`BIGNUMERIC`を使用し、費目別総額と税区分を保持する |
| 品質 | 48コマ、単価、電力量、金額、SCD、制度適用、公開可否を検証する |
| 公開 | BIは原則GoldまたはServingだけを参照する |
| PII | 需要家の原PIIをRestricted領域へ分離し、Policy Tag等で制御する |
| 例外 | 制度、約款、請求仕様に起因する例外だけを承認付きで採用する |

## 3. 業務時間軸と単位

### 3.1 30分コマ

1日は48コマとする。`slot_number`は1から48までの整数で管理する。コマの帰属日は開始時刻が属する日とする。したがって、23:30から24:00までのコマ48は当日に帰属する。

電力業務の主キーは、必要に応じて`target_date`、`slot_number`、エリア、BG、地点、流向、セグメント、メニュー種別を組み合わせる。`target_date`と`slot_number`を業務上の時間キーとし、表示・外部連携時にJSTの時刻へ変換する。

### 3.2 単位

計画値はkW、実績値と約定量はkWhを標準とする。30分平均電力から電力量へ変換する場合は、`kW × 0.5h = kWh`を明示する。受電端と送電端を混在させず、インバランス計算前に基準を統一する。

需要実績の送電端換算は、送電損失率を`loss_rate`として次式で行う。

```text
送電端換算電力量 = 受電端電力量 ÷ (1 − 送電損失率)
```

### 3.3 税と丸め

JEPX価格、インバランス料金、託送料金、容量拠出金、手数料は、ソースの税区分を保持する。再エネ賦課金は公表値を税込で保持し、日次・コマ段階では税込総額を保持する。BronzeとSilverでは数値を丸めない。税抜化と請求仕様に基づく丸めはGoldの月次精算で行い、丸め前の値と調整額を保持する。

税率はハードコードせず、対象日で消費税マスタを解決する。費目ごとの金額を保持し、合成単価を原則として作成しない。

## 4. データレイヤーと物理配置

### 4.1 Bronze

外部・社内ソースを無加工で保持する。JEPX、一送、OCCTO、GIO、気象、自社需給システムからのファイルまたはレコードに、`source_system`、`file_name`、`received_at`、`file_hash`、`batch_id`、`ingestion_run_id`を付与する。再送ファイルは上書きせず、Silver側で最新採用・重複排除を行う。

### 4.2 Silver

Silverは事実を正規化する層であり、`dim_`、`fact_`、`v_`を使用する。型変換、単位統一、エリアコード名寄せ、重複排除、SCD Type 2、実績クレンジングを行う。損益、休日解釈、粗利、BG内部精算などの業務判断はGoldまたは専用計算処理に置く。

速報、確報、確定の実績はライフサイクルが異なるため、物理的に分離する。

| 実績層 | 目的 | 標準保持 |
|---|---|---|
| 速報 | 当日監視、時間前調達判断 | 速報本体・最新行キャッシュを短期保持 |
| 確報 | 日報、粗利分析 | 確定値への切替前まで保持 |
| 確定 | 請求、公的精算、監査 | 業務保持要件に従い長期保持 |

統合ビューは「確定、確報、速報」の優先順で1本の時系列を返す。確定値受領状況により層境界を動的に判定し、確定・確報・速報の二重計上を防ぐ。

### 4.3 Gold、Serving、Quarantine、Audit

Goldは日報損益、インバランス、月次精算、予測精度などの業務資産を提供する。ServingはLooker Studio抽出、API、業務処理など、利用目的とSLAに合わせて最適化した公開資産を提供する。品質不合格、未名寄せ、変換不能データはQuarantineへ隔離する。バッチ実行、品質判定、単価解決、再処理、マスタ変更はAuditへ記録する。

## 6. マスタとSCD Type 2

料金メニュー、契約、託送、送電損失率、容量拠出金、再エネ賦課金、燃料費調整、FIP、BG、休日ルールなど、対象日で値が変わる資産は期間管理する。期間結合には必ず対象日条件を付与する。

```sql
fact.target_date BETWEEN master.start_date AND master.end_date
```

同一業務キーで期間重複を禁止する。契約履歴では隙間を原則エラーとするが、解約・再契約など真の無契約期間を許す場合は、業務判断と専用処理を登録する。確定計算に使用したマスタID、パラメータID、税率ID、制度年度をGoldへ記録する。

## 7. 業務ファクト

### 7.1 実績

需要・発電実績は30分コマで保持する。受電端、送電端、速報、確報、確定、補完フラグ、確定値受領状況を区別する。確定層の訂正は、業務要件上許される場合を除き上書きせず、打ち消し・訂正レコードと監査履歴で追跡する。

### 7.2 計画と市場

計画と実績を別資産にする。計画には計画種別、版、提出時刻、計画基準を保持する。JEPX価格、約定明細、インバランス単価、先物、相対・PPA、非化石証書を別ファクトとして管理し、約定原価とみなし原価を混同しない。

### 7.3 日報損益

日報損益マートの標準粒度は次のとおりとする。

```text
対象日 × コマ × エリア × BG × 流向 × セグメント × メニュー種別
```

`direction`は需要を`INBOUND`、発電を`OUTBOUND`、蓄電を`STORAGE`とする。需要と発電の行をセグメント名だけで区別しない。売上・原価は費目別総額の和として保持し、適用単価参照、データ状態、検算フラグを付与する。

## 8. 日報・精算ロジック

毎日のバッチは、前提チェック、カレンダー解決、地点属性解決、実績正規化、売上計算、インバランス計算、調達原価計算、粗利集計、検算、Serving更新の順に実行する。48コマ欠落、単価未解決、対象日の市場価格未着、確報未完了などがある場合は、中途半端なGoldを公開しない。

固定単価、燃料費調整、再エネ賦課金、市場連動単価、JEPX調達、相対・PPA、インバランス、託送、容量拠出金、非化石証書、FIPプレミアム、発電側課金は費目別に計算する。市場調達原価は約定明細を起点とし、需要量×単価だけで代替しない。

BG按分はコマ単位で行い、按分額の合計がBG総額と一致することを検証する。分母が0の場合は0埋めせず、NULLまたは要確認として公開ゲートで検知する。

## 9. データ品質と公開ゲート

最低限、次を日次検算する。

| 検算 | 合格条件 |
|---|---|
| 48コマ | 地点・日単位で欠番がない。例外は補完フラグとともに記録する |
| 単価網羅 | NULL単価で計算された行が0件 |
| 電力量 | 需要、発電、約定、インバランスの突合が許容差以内 |
| 金額 | 費目の和と売上・原価・粗利が一致する |
| 主キー | 重複0件 |
| 流向整合 | `INBOUND`、`OUTBOUND`、`STORAGE`の値域が正しい |
| 期間管理 | 適用期間の重複・逆転・不要な隙間がない |
| 月次請求 | 約款・請求仕様の丸め後に1円単位で突合する |
| 公開可否 | Critical品質エラーがない |

検算NGの場合、新しいBI抽出を公開しない。前回正常版を保持し、`agg_data_quality_daily`等のAudit資産に判定、件数、差額、原因、再処理状況を記録する。

## 10. クレンジングと補完

クレンジングはSilverで行い、変更前の値、変更理由、補完方法、補完フラグを保持する。太陽光の夜間ゼロ、風力のカットアウト、訪問検針のプロファイル配分、推定検針、物理限界超過を同一ルールで処理しない。試運転期間の発電実績は、売電・FIP・発電側課金の業務判定と整合するように扱い、通常の欠損補完を無条件に適用しない。

補完率、欠番率、推定検針数、未名寄せ数をDQマートへ記録する。補完が一定閾値を超えた地点は日報公開または分析利用を制限し、照会・再処理を行う。

## 11. BIとServing

Looker Studioは原則ServingまたはGoldの抽出用資産だけを参照する。Silver、未加工JSON、未集約ARRAYを直接公開しない。抽出更新は、日報バッチ完了、検算、抽出更新、完了確認、公開通知の順序を守る。検算NG時は新しい抽出を公開せず、前回正常版を表示する。

コマ粒度のライブ接続と、日報・経営向けの抽出データソースを分離する。抽出用ビューには検算通過フラグ、抽出生成日時、対象期間、公開可否を含める。

## 12. 外部データとスケジュール

DTSは対応する外部サービスの標準転送、Cloud Run Jobsは独自APIや大規模取得、Cloud Functionsは軽量なイベント処理に使用する。外部APIは指数バックオフ、4xxと5xxの扱い分け、レート制御、ページング、チェックポイント、再開位置を実装する。

DTS完了をテーブルポーリングだけで検知しない。完了イベント、転送状態、受領件数、対象期間を組み合わせ、重複イベントを冪等に処理する。DataformまたはStored Procedureの起動条件をAuditへ記録する。

## 13. 保持、監査、DR / BCP

保持期間はデータ資産単位に、法令、契約、請求、監査、再計算、削除要求、費用、RPO / RTOで決定する。電力基盤の確定値、制度単価、月次精算、監査ログは長期保持を基本候補とするが、全資産へ一律の期間を適用しない。

確定値、請求突合、BG精算、制度費用について、指定時点の復元と再計算ができることを検証する。Time TravelをSCD履歴や業務上のPIT照会の代替にしない。復元テストではデータ、IAM、Policy Tag、Row Access Policy、BI接続、監査証跡、重複なし再処理を確認する。

## 14. アンチパターンと対応案

以下は、汎用ガイドまたは電力業務要件に反する代表的なアンチパターンである。個別実装で採用してはならない。業務上避けられない場合は、例外管理を行う。

| アンチパターン | 問題 | 対応案 |
|---|---|---|
| `d_`、`f_`、`m_`を新規標準として使用する | 正規の命名規則と一致せず、資産種別が統一できない | `dim_`、`fact_`、`agg_`へ統一し、既存資産は互換ビューと移行期限を設ける |
| 10GBや数百万行だけでパーティションを決める | 小規模な過分割や、アクセスに合わないパーティションが生じる | クエリ、保持、更新、BI、dry run、bytes processedで判断する |
| 高カーディナリティ列を必ずクラスタ先頭にする | 実際のWHERE、JOIN、集計に効かない場合がある | 電力のエリア、地点、BG、流向等を候補にし、実ワークロードで列順を検証する |
| すべてのファクトを無条件に`target_date`パーティションにする | 速報ストリームや取込監査では最適でないことがある | 速報は取込日、確報・確定・日報は対象日など、用途とアクセスで選ぶ |
| `require_partition_filter`を設定したが、DataformやBIを検証しない | バッチや抽出が実行時に失敗する | 直接SQL、Dataform、BI、バックフィル、復旧処理を受入テストする |
| 受電端と送電端の値をそのまま差し引く | インバランスと電力量突合が誤る | インバランス算定前に送電端へ統一し、基準を列と契約へ記録する |
| kWとkWhを同じ列や同じ計算式で扱う | 30分換算の誤りにより金額・需給が崩れる | 単位を列説明に記載し、kW×0.5hの変換を明示する |
| 速報、確報、確定を1テーブルで上書きする | 確定値が更新で破壊され、成熟度を追跡できない | 物理分割し、確定・確報・速報の優先統合ビューを作る |
| 確定値を通常のUPDATEやDELETEで訂正する | 請求・監査結果の再現性が失われる | 訂正・打ち消しレコードと監査履歴を用い、承認済み再処理を行う |
| 単価NULLを0で埋めて日報を続行する | 売上・原価が過小計上され、欠陥が隠れる | NULLのまま停止し、単価未解決をDQとアラートへ記録する |
| コマごとに金額を丸める | 月次請求との間に数円の差が発生する | Bronze/Silverは未丸め、月次精算で請求仕様に従って一度だけ丸める |
| 合成単価だけを保持する | どの費目が差異原因か追跡できない | JEPX、託送、容量、賦課金、手数料等を費目別総額で保持する |
| JEPX約定量と需要量を同一視する | 実際の約定と調達原価が一致しない | 約定明細を原価の起点とし、必要な場合だけ根拠付きで按分する |
| BG按分を月次総量だけで行う | コマ単位の原因者、端数、免責条件を失う | コマ単位で按分し、合計一致と端数処理を検証する |
| 同じセグメント列だけで需要行と発電行を区別する | 主キー衝突や粗利更新の誤りが起きる | `direction`を主キーと判定条件へ含める |
| FIPのA値や制度単価をコードへ埋め込む | 改定・洗替・年度変更に対応できない | 年度・適用期間付きマスタと確定値参照IDで管理する |
| 再エネ賦課金を他費目と同じ税抜計算にする | 請求値と一致しない | 税込保持、月次総額、請求仕様の丸め・税抜化を分離する |
| 試運転中のゼロや急変を通常異常として補完する | 試験・抑制の実態を破壊する | 試運転期間を判定し、補完、売電、FIP、課金の扱いを個別に決める |
| 太陽光の夜間ゼロと風力のカットアウトを同じ補完にする | 電源特性を無視した誤補完になる | 電源種別・気象・試運転属性に基づき補完ルールを分ける |
| 祝日CSVの取込失敗時に空のカレンダーを更新する | 料金休日が平日に上書きされる | 受入判定、検疫、前回正常版維持、アラート、影響日更新を行う |
| 個人情報を「必要になったら」保護する | 初期環境やBI経由で過剰公開される | 初期から分類・分離・権限を定義し、Policy Tagは段階導入する |
| `secret.tfvars`へ秘密を記載する | stateやログへ秘密が残る可能性がある | Secret実値をTerraformに渡さず、承認済みSecret登録経路を使う |
| Workflowsの未検証YAMLを汎用標準にする | 製品仕様・構文差で本番失敗する | バージョン固定のImplementation GuideとCI検証へ分離する |
| BigQuery Jobの完了をHTTP成功だけで判定する | 非同期ジョブの失敗を成功扱いする | `state`、`errorResult`、`errors[]`、実行ID、対象範囲を判定する |
| 検算NGでも新しいBI抽出を公開する | 誤った日報を利用者へ配布する | 公開ゲートで停止し、前回正常版を維持する |
| コマ粒度をそのままLooker抽出へ投入する | 抽出容量・性能・操作性が悪化する | コマ粒度ライブ接続と、日次・経営向け抽出を分離する |
| 10年保持を全資産へ無条件適用する | 法令、削除、費用、運用要件と不整合になる | 資産ごとに保持、RPO、RTO、削除、コストを評価する |

- [ ] 1行の粒度、主キー、単位、時刻基準が定義されている。
- [ ] 30分コマ、コマ48、対象日帰属が定義されている。
- [ ] 受電端と送電端、kWとkWh、税込と税抜が区別されている。
- [ ] `dim_`、`fact_`、`agg_`、`v_`等の命名に適合している。
- [ ] 期間管理の重複・逆転・隙間の扱いが検証されている。

### 15.2 品質・公開

- [ ] 48コマ欠番、単価NULL、主キー重複、金額・電力量突合を検証している。
- [ ] 補完前後の値と補完理由を追跡できる。
- [ ] Critical品質エラーでGold / Serving公開が停止する。
- [ ] 前回正常版、再処理方法、通知先が定義されている。

### 15.3 セキュリティ・運用

- [ ] 原PIIがRestricted領域へ分離されている。
- [ ] サービスアカウントの責務が分離されている。
- [ ] Secret実値がコード、state、ログ、辞書へ露出していない。
- [ ] 実行ID、バッチID、パイプライン版、適用単価IDを追跡できる。
- [ ] RPO / RTO、復元テスト、問い合わせ先、エスカレーションが定義されている。

## 16. セキュリティ・コスト統制の正式追加

### 16.1 電力データ分類

| 区分 | 対象例 | 標準制御 | 公開範囲 |
|---|---|---|---|
| PII | 氏名、住所、連絡先、個人契約情報 | Restricted領域、Policy Tag、原値分離 | 権限付与された業務担当のみ |
| 契約・地点機微 | 供給地点特定番号、契約履歴、料金メニュー | 列制御、顧客・エリア単位の行制御 | 契約・営業・精算担当 |

| 取引機密 | JEPX約定、PPA単価、先物、手数料 | 取引担当と監査担当へ限定 | トレーディング・精算 |

### 16.5 電力基盤の受入テスト追加項目

### セキュリティ

- [ ] 供給地点特定番号、需要実績、約定、契約単価、粗利の分類が登録されている。
- [ ] 業務ロール、エリア、BG、顧客、契約単位のアクセス検証が完了している。
- [ ] 原PII、疑似識別子、契約単価、約定、監査ログの権限が分離されている。
- [ ] 確定値、制度マスタ、BG精算の訂正・変更が承認制である。
- [ ] Extract、Copy、BI、SFTP等の外部出力を追跡できる。
- [ ] 速報監視、日報、月次精算、確定値のRPO / RTOと復元結果がある。

### コスト

- [ ] 日報バッチの対象日限定と費用ベースラインがある。
- [ ] 月次精算と長期バックフィルの事前費用見積もりがある。
- [ ] 速報ストリーム、最新行キャッシュ、確報のTTLと費用が検証されている。
- [ ] BI抽出の対象期間、更新頻度、費用が登録されている。
- [ ] 速報、日報、月次、BI、バックフィル、DQのReservation方針がある。
- [ ] 10年保持のActive、Long-term、Time Travel、Fail-safe、GCS二重保存を含む費用モデルがある。

### 16.6 既存アンチパターンへの追加

| アンチパターン | 問題 | 対応案 |
|---|---|---|
| 供給地点特定番号を一般BIへ直接公開する | 契約・地点の再識別と過剰共有が起きる | 疑似識別子、Policy Tag、認可ビュー、顧客・担当者単位の行制御を使用する |
| JEPX約定・PPA単価・粗利を同じBI権限で公開する | 取引機密と経営機密の漏洩範囲が拡大する | 取引、精算、経営向けServingを分離し、列・行制御を適用する |
| 10年保持を理由に全データを無期限にBigQueryへ残す | 不要なストレージ、Time Travel、GCS二重保存が増える | 資産別保持、TTL、法的保持、長期保存費用を評価する |
| 月次確定後に全期間を一括再計算する | Slot、処理時間、費用が急増する | 影響期間・エリア・制度費目に限定し、承認済み分割バックフィルを行う |
| 速報ストリームをBIのライブ接続から直接参照する | 高頻度スキャンと抽出費用が増加する | 最新行キャッシュ、監視専用ビュー、Serving集計を利用する |
| 制度マスタを担当者が直接本番更新する | 適用期間・計算結果・請求値の監査性が失われる | 根拠資料、二者承認、ステージング検証、差額試算、監査ログを必須化する |
| 費用異常時に日報・精算・速報を同時停止する | 業務影響が過大になる | 非必須BI・バックフィルから停止し、重要処理の優先順位を定義する |
